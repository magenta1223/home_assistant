# 메모리·주제 재정리의 운영 참고

[구조 탐색 본문](memory-consolidation-and-topic-hierarchy.md)의 설계를 구현할 때 다시 검토할 운영·검색·평가 참고안이다. 현재 우선 과제는 Memory와 Topic의 객체 분리이며, 아래의 단계·정책·수치·단일 기본 부모 가정은 확정된 구현 요구가 아니다. 새로운 Topic 모델이 정해지면 그 모델에 맞게 다시 판단한다.

Memory의 근거와 immutable ACL을 보존한다는 원칙은 계속 유효하다. 운영 순서와 자동화는 그 원칙을 구현하는 후속 선택이다. 이 문서는 DB 초기화·관계 삭제·운영 작업 실행을 지시하거나 승인하지 않는다.

## 1. 권한과 근거 보존

### 1.1 요약 이후 필터링은 늦다

비공개 memory를 사용해 만든 요약은 child를 숨겨도 그 내용이 남는다. 제목도 마찬가지다. 공개 기록에는 ‘병원 예약’만 있는데 비공개 기록을 읽어 제목을 특정 질환명으로 바꾸면 제목에서 정보가 샌다.

따라서 ACL은 모델 입력과 파생 정보 생성 전부터 적용해야 한다. 조회 시 child만 필터링하는 것으로는 충분하지 않다. 검색 embedding, 요약 문자열, 후보 설명, 수정 이력, 로그까지 같은 정보 경계를 고려해야 한다.

### 1.2 첫 버전은 정확히 같은 access scope별로 묶는 편이 단순하다

권장 초기 규칙은 PUBLIC끼리, 또는 정렬된 allowed user ID 집합이 정확히 같은 RESTRICTED끼리 주제를 만든다는 것이다. 작성자가 다르더라도 access scope와 대상·영역이 같다면 후보가 될 수 있다. 반대로 같은 작성자의 기록도 열람 범위가 다르면 구분한다.

이는 `UserId` 기반 immutable ACL을 유지하며 구현 난이도를 줄이는 보수적인 제안이다. 서로 다른 scope의 요약을 꼭 지원해야 한다면 근거들의 열람 가능 사용자 교집합으로 제한할 수 있지만, 정보가 과도하게 숨겨지고 요약 범위가 이해하기 어려워진다. 초기에는 그러한 교차 scope 통합을 하지 않는 편이 낫다.

현 `MemoryAccess.intersection`은 PUBLIC을 중립으로 두고 RESTRICTED 사용자 집합을 교차시키며 빈 교집합을 거절한다. 새 파생 정보에서도 누출 방지 원칙은 이어받아야 하지만, 기존 사실이나 SourceRecord의 access를 변경하는 방식으로 구현해서는 안 된다.[^L9]

### 1.3 두 가지 안전한 주제 표현

첫째, 같은 scope 내 주제를 만든다. 예를 들어 PUBLIC 보일러 주제와 특정 사용자들만 보는 보일러 주제가 별도로 존재할 수 있다. 일부 중복은 보안의 결과이며 파편화 제거 대상으로 무조건 취급하지 않는다.

둘째, 원래부터 공개 가능한 중립적 주제명에 사용자별 visible 구성원을 조합한다. 이때 제목·범위 설명 자체가 비공개 근거에서 추론된 것이어서는 안 된다. 사용자별 요약을 만들면 사용자 또는 정확한 scope와 근거 버전이 cache key에 들어가야 한다.

첫 버전은 첫째가 더 단순하다. 이후 한 화면에서 중립적 공통 제목으로 합쳐 보여 주는 read projection은 필요할 때 검토할 수 있다. 보이지 않는 구성원의 개수나 존재 여부를 부가 정보로 노출해서는 안 된다.

### 1.4 provenance와 확실성

파생 주제·요약은 사용한 memory ID와 생성 당시 버전을 추적해야 한다. 요약 문장의 근거까지 연결할 수 있으면 더 좋다. 원래 Memory의 evidenceRefs는 그대로 유지한다.

요약을 반복 생성한다고 사실의 certainty가 올라가지 않는다. ‘발화했다’, ‘관찰되었다’, ‘추정했다’라는 의미를 보존해야 하며, 상충하는 기록을 묶을 때는 충돌을 감추지 않는다. 상위 주제 자체는 영역을 조직할 뿐 어떤 사실의 진위를 보증하지 않는다.

`createdAt`은 현재 모델에서 저장 시각이지 사건 발생 시각이 아니다. 카카오 과거 기록을 오늘 분석했다는 이유로 사건들이 오늘 일어났다고 요약해서는 안 된다. 기간과 변경 이력은 원문 근거의 실제 시간 표현을 이용해야 한다.[^L4]

## 2. 실행 경계, 실패, 복구

### 2.1 입력 수집과 구조 정리를 분리

사실을 안전하게 저장하는 성공과 주제 정리에 성공하는 것은 별개다. 권장 흐름은 canonical memory 저장 후 별도 정리 제안을 만들고, 검증·적용하는 것이다. 정리 실패 때문에 원래 evidence-backed memory를 버리거나 수집 성공을 취소하지 않는다.

현재 분석 흐름도 indexing과 placement 실패가 canonical commit을 취소하지 않는 구조다. 그러나 기존 placement에는 영속 실패·재시도가 아직 없다는 완료 기록이 있다. 자동 주제 정리까지 추가할 경우 best-effort 호출만으로 복구가 보장된다고 설명해서는 안 된다.[^L10]

### 2.2 원자적 변경과 오래된 제안 차단

유지보수는 snapshot을 읽고 모델에 제안을 받는 동안 다른 입력이 들어올 수 있다. 현재 process-local mutex는 placement 실행만 직렬화하며 다른 프로세스·새 정리 작업과의 경쟁을 자동으로 해결하지 않는다. 따라서 apply 직전에 대상 version 또는 현재 관계를 다시 확인해야 한다.

부모 변경, 주제 생성, 구성원 이동, 병합 대표화는 한 transaction의 최종 구조로 검증한다. 적용 결과에는 self-link·cycle·다중 기본 부모·존재하지 않는 ID·범위 밖 대상·의도치 않은 memory 소실이 없어야 한다. snapshot이 낡았으면 변경 없이 거절하고 재제안한다.

재정리 작업의 idempotency는 원래 source 분석의 idempotency와 다르다. 최소한 scope·대상 snapshot·정리 계획을 구분할 수 있어야 하며, 재실행이 같은 주제를 반복 생성하지 않도록 해야 한다.

### 2.3 복구는 원자 사실 복원보다 projection 복원이 쉬워야 한다

원자 사실을 건드리지 않는 설계에서는 잘못된 주제 정리를 이전 topic/membership 상태로 돌릴 수 있다. 변경 전후와 적용 ID를 기록하고, 새 주제·연결을 취소하는 방법이 필요하다. 처음에는 스냅샷과 명시적 undo로도 충분하며 전체 event-sourcing 플랫폼은 필요하지 않다.

병합된 Topic ID를 삭제하면 이전 링크가 깨질 수 있으므로 대표 주제 연결 또는 inactive 상태를 검토한다. 기존 Memory ID를 Topic ID로 치환하거나 다시 번호를 부여하지 않는다.

### 2.4 인덱싱과 요약 신선도

현재 placement에서 부모를 다시 embedding하지 않는 이유는 content가 바뀌지 않기 때문이다. 상위 summary나 검색용 scope description을 실제로 변경하는 새 기능에서는 이 전제가 달라진다. 검색 가능한 파생 내용이 바뀌면 인덱스도 갱신되어야 한다.[^L10]

지속적인 검색용 summary를 도입할 경우 DB 확정과 인덱스 갱신 요청은 원자적으로 기록하고, 외부 인덱스 실패는 재시도할 수 있어야 한다. 기존 canonical indexing outbox와 같은 원칙을 적용할 수 있지만 현재 계약을 검토 없이 그대로 재사용한다고 확정해서는 안 된다.

변경된 membership에 대해 예전 요약을 최신으로 표시하지 않는다. 요약을 dirty로 표시하고 이전 요약을 숨기거나 구버전임을 명시한 뒤, 새 요약이 성공했을 때 교체한다. 실패 시 직접 memory 검색과 기본 탐색은 계속 가능해야 한다.

### 2.5 가정 Review와 분리

보류된 가정 Review는 중요한 변화·미완료 작업·다가오는 문제를 브리핑하는 읽기 기능이며 Memory를 임의 수정하지 않도록 정의되어 있다. 내부 주제 구조를 변경하는 consolidation과 책임이 다르다.[^L11]

이번 문제의 해결을 Review·Task·Notification 구현에 종속시키지 않는다. 또한 이번 보고서는 scheduler, 반복 automation, 운영 정리 작업의 실행 승인이 아니다. 운영 실험이 필요해질 때 별도 범위와 백업·복구 계획을 확인해야 한다.

## 3. 검색과 탐색에 적용하는 방식

### 3.1 첫 단계는 화면 조직만 바꿔도 된다

불편함이 ‘기억을 보는 화면에서 상위 목록이 읽기 어렵다’라면, 주제 뷰가 먼저다. 원자 메모리 검색·답변 생성은 유지하고, 별도의 파생 Topic projection으로 주제별 탐색을 제공하면 문제와 해결의 연결이 가장 명확하다.

조회 요청마다 LLM으로 전체 트리를 재군집화하는 것은 권하지 않는다. 비용·지연뿐 아니라 새로고침마다 주제 구조가 달라질 수 있기 때문이다. 초기 실험에서는 고정된 입력 snapshot으로 한 번 만든 제안을 읽기만 하고, 운영 단계에서는 변경 후 projection을 유지한다.

### 3.2 구체 질문은 직접 사실 검색을 유지

‘보일러 모델명이 뭐지?’ 같은 질문은 원자 memory를 직접 검색하고 해당 evidence에 근거해 답한다. 상위 요약 하나를 찾고 나머지 경로를 추측하는 방식으로 대체하지 않는다.

‘보일러 관련 정보를 정리해 줘’ 같은 질문은 Topic이 관련 구성원 후보를 좁히는 데 도움을 줄 수 있다. 그러나 실제 답변에는 필요한 memory를 관련도와 토큰 budget에 맞춰 선택해야 한다. topic 아래 모든 자손을 무조건 프롬프트에 넣는 것도 피한다.

‘우리 집 설비 중 최근 문제가 반복되는 것은?’ 같은 질문은 여러 topic과 사건의 기간·반복 근거가 필요하다. 이 정도 전역 질문의 요구가 실제로 쌓인 뒤 summary와 넓은 검색 경로를 도입하는 편이 합리적이다.

### 3.3 깊이는 평가 결과로 정한다

현재 placement 부모 노출 깊이 2와 답변 확장 깊이 1을 고려하면, 첫 주제 실험은 얕은 구조가 안전하다. 안정적인 영역과 구체 대상 정도의 단계부터 검토한다. 하지만 모든 가족 기록에 두 계층을 강제하거나 그 수치를 영구 제약으로 만들 필요는 없다.

주제 검색을 추가할 때는 그룹·세부 사실을 함께 후보로 유지하는 방식, 또는 상세 memory에서 필요한 ancestor를 추가하는 방식을 비교할 수 있다. RAPTOR와 TiMem이 다른 방향의 계층 검색을 보여 주므로 ‘계층형 기억에는 정답인 검색 방향 하나가 있다’고 가정하지 않는다.[^3][^11]

## 4. 단계별 도입 권고

### 단계 A: 실제 문제 분류

등록 사용자에게 보이는 트리 snapshot에서 대표 사례를 추린다. 제목이 다른 같은 주제, 같은 대상의 분산된 사실, 적절한 상위 주제 부재, 특정 사실을 폴더로 사용한 경우, ACL 때문에 정상적으로 분리된 경우를 각각 표시한다. source 원문은 필요할 때 해당 권한 범위 안에서 확인한다.

산출물은 ‘루트가 많다’는 총평이 아니라 정리 전후의 구체 사례다. 일괄적으로 줄일 대상과 보존할 대상을 구분해야 한다. 현재 보고서에는 운영 데이터가 없으므로 이 측정은 향후 실험의 첫 단계다.

### 단계 B: 변경 없는 재정리 제안

같은 scope의 작은 집합을 대상으로 새 주제명·범위·구성원 연결을 제안한다. 기존 사실은 수정·삭제하지 않으며 생성·이동 예상 결과를 보여 준다. 이 단계에서는 scheduler, 자동 승인, 새로운 서버가 필요하지 않다.

소규모 사용자 검토는 제품에 영구적인 승인 업무를 추가하기 위한 것이 아니라 기준을 학습하는 실험이다. 가족이 이 주제명으로 필요한 기억을 찾을 수 있는지, 과도하게 합친 사례가 없는지 확인한다.

### 단계 C: 최소 durable Topic projection

반복해서 유용한 정리 기준이 확인되면 작은 Topic·membership 상태를 저장한다. 기존 Memory ID·content·evidence·ACL은 유지한다. 주제 조회를 기존 HTTP 인증 경계 안에 추가하고, 적용 전후 기록과 undo를 제공한다.

최초 버전의 성공 조건은 사용자 탐색 개선이다. 요약 검색, 장기 프로필, 자동 추론은 제외할 수 있다. ports, orchestration, 실패 계약이 바뀌면 가장 가까운 use-case README를 함께 갱신해야 한다.

### 단계 D: 필요 기반의 국소 유지보수

새 입력에는 기존 주제 재사용을 우선한다. 구조 점검은 명시적 요청 또는 실제 파편화 신호가 생긴 범위부터 수행한다. 매우 비슷한 형제 주제 증가, 관련성이 낮아진 큰 주제, 반복적인 잘못된 배치가 후보 신호다.

정리 결과를 이전 상태와 비교해 개선이 작으면 NOOP한다. 새 정보가 없는데 비슷한 주제들 사이에서 계속 왕복 이동하는 현상을 막기 위해 최소 개선 조건과 변경 이력을 사용할 수 있다. 구체 수치는 실제 샘플로 조정한다.

### 단계 E: 검증 후 자동화·검색 확대

변경 안전성, 실패 후 재시도, scope 격리, 요약 provenance가 확보되면 백그라운드 실행을 검토한다. 정리할 것이 없으면 모델 호출과 알림을 억제한다. 처리량·토큰 사용량·최대 실행 시간을 제한한다.

기존 검색보다 주제 기반 context가 개선되는 질문 유형에만 검색 확장을 적용한다. 정리 후 질의가 매우 적다면 자동 요약 유지비를 내지 않는 편이 나을 수 있다. 데이터 입력량과 조회량을 함께 보고 결정한다.

## 5. 평가와 회귀 테스트

### 5.1 성공 지표

| 관점 | 측정할 것 | 주의할 점 |
|---|---|---|
| 탐색 | 대표 질문의 memory를 찾는 시간·경로·성공 여부 | 루트 수 감소만 성공으로 보지 않음 |
| 구조 | 중복 주제, 부적절한 기본 부모, 과대 주제 사례 | 보안상 분리를 중복으로 오인하지 않음 |
| 검색 | 정답 memory/evidence의 후보 포함과 최종 답변 | 구체 사실 질문의 성능을 유지 |
| 시간 | 현재·과거 상태 구분, 사건 순서 | 저장 시각을 사건 시각으로 쓰지 않음 |
| 신뢰성 | 요약의 근거 연결, 모름·충돌 표시 | 반복 요약을 새 증거로 계산하지 않음 |
| 보안 | 제목·요약·검색·로그·cache 누출 | 누출 허용 목표는 0 |
| 안정성 | 새 정보 없을 때 구조 변경량, stale plan 거절 | 과도한 재배치가 이득이라고 단정하지 않음 |
| 운영 | 실행당 모델 토큰, 실패·재시도, undo 가능성 | 조회량 대비 유지 비용도 평가 |

메모리 사실 수 감소는 이번 기능의 목표가 아니다. 사실의 수가 같더라도 찾기 쉬운 주제 구조가 생겼다면 성공할 수 있다. 반대로 root가 한 개로 줄어도 ‘가족 정보’ 하나에 모든 것이 들어간다면 실패다.

### 5.2 질문 세트

실제 가족 용어를 사용하는 작은 고정 질문 세트부터 만든다. 예를 들어 20~30문항은 시작 규모의 제안이지 통계적으로 충분한 검증을 보장하는 숫자가 아니다. 질문별 정답 memory와 필요한 evidence를 미리 정하고 정리 전후를 비교한다.

- 구체 사실: 모델명, 연락처, 보증 기간, 특정 합의.
- 동일 주제 종합: 한 설비의 설치·수리·사용 제약.
- 여러 주제 종합: 집 설비의 보증·유지보수 현황.
- 시간 변경: 과거 주소와 현재 주소, 교체 전후 장비.
- 동명이인·동일 명칭: 같은 이름의 다른 가족·다른 집·다른 장비.
- 반복 사건: 비슷한 문장이지만 날짜가 다른 거래·수리.
- 모름·충돌: 근거 없는 정보, 상충하는 최신 기록.
- ACL: 동일 질문을 서로 다른 사용자로 실행한 결과 차이.

### 5.3 필요한 테스트

Application에서는 범위 밖 ID, 중복 assignment, self-link, cycle, 다중 기본 부모, stale snapshot, 빈 후보, NOOP, 잘못된 모델 응답을 검증한다. 원자 memory 집합과 내용이 보존되는지 확인한다.

Persistence에서는 새 topic과 이동이 전부 적용되거나 전부 rollback되는지, 재실행 시 중복 topic이 없는지, 실패·프로세스 중단 후 복구되는지 검증한다. 명시적 undo도 확인한다.

ACL 테스트에는 private content로 public 제목·요약을 생성하지 않는 경우, 다른 RESTRICTED 집합 간 비의도적 병합 차단, hidden parent 아래 visible child가 여전히 보이는 경우, 비공개 구성원 수 미노출을 포함한다. 모델 입력·출력과 cache를 통해 scope가 섞이는지도 확인한다.

검색 회귀에서는 새 계층 아래 들어간 세부 memory가 직접 검색되는지, summary가 오래됐을 때 사실로 돌아가는지, 다수 child와 추가 depth에서 근거가 누락되는지 검증한다. 기존 요청 중복 방지와 십 분 conversation idle lease는 재정리 기능의 변경 대상이 아니다.
