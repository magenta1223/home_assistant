# 가족 Second Brain의 메모리 파편화와 주제 계층 재정리

## 1. 결론

상위 메모리가 계속 잘게 늘어나는 문제는 새로운 문제가 아니다. 전통적인 지식조직에서는 주제어 정규화와 분류체계 유지보수로, 최근 LLM 기억 시스템에서는 memory consolidation, hierarchical abstraction, dynamic restructuring이라는 이름으로 다뤄 왔다. 특히 xMemory는 상위 그룹이 너무 파편화되거나 너무 넓어지는 문제를 명시적으로 함께 다룬다.[^1][^2]

이 프로젝트의 핵심 방향은 **Memory는 사실로 축적하고, Topic은 교체 가능한 조직 구조로 분리하는 것**이다. 같은 사실의 중복, 같은 대상의 다른 사실, 더 넓은 영역, 단순 관련성, 시간 변화, 추론은 서로 다른 관계다. 한 종류의 부모·자식 연결이나 문장 병합으로 모두 처리하지 않는다.

현재 구현은 신규 원자 메모리를 다른 메모리의 부모로 선택할 수 있다. ‘새 상위 메모리가 만들어지지 않는다’는 진단은 부정확하다. 다만 사실이 상위 역할을 겸하며 별도 Topic을 만들지는 않고, 누적된 조직 구조를 다시 병합·분할·재배치하는 과정도 없다.[^L1][^L2][^L3]

현재 설계 탐색에서는 기존 시스템을 SourceRecord와 Canonical Memory까지의 기반으로 본다. 기존 Memory 간 부모 관계는 반드시 유지할 자산이 아니다. 데이터가 적고 다시 구성할 수 있으므로 migration 비용은 구조 선택의 제약으로 두지 않는다. 별도 기억 서비스나 프레임워크는 도입하지 않고 기존 애플리케이션 안에서 직접 구현하는 것을 전제로 한다.

따라서 먼저 정할 것은 Topic의 정체성과 범위, Memory 소속, Topic 간 계층·관련 관계다. Topic 구조를 바꾸어도 Memory의 내용·출처·시간·권한은 바뀌지 않아야 한다. 계층 밖의 링크와 장기 사용을 위한 수치적 배치·재정리 판단은 11번에서 다룬다. 운영 자동화·배포·복구의 상세 순서는 구조를 정한 뒤 다룬다.

이 권고는 문헌의 설계 요소를 가족용 시스템에 맞게 선별한 판단이다. 특정 연구의 전체 아키텍처나 성능이 이 프로젝트에도 그대로 적합하다는 뜻은 아니다.

## 2. 문제의 범위와 판단 수준

### 2.1 조사 범위

검토 범위는 지식조직 표준, 계층형 RAG, 동적 트리 기억, 그래프 기억, 사실 통합, 파생 요약, 백그라운드 유지보수다. 문헌과 제품 문서는 2026년 9월 14일 확인 기준이다. 논문은 RAPTOR, MemTree, Mem0, A-MEM, Zep, Hindsight, TiMem, xMemory를 중심으로 비교했다. 수치적 배치·링크·재정리 기준은 기존 1–18번 자료에 한정하여 검토한다. 고전 군집 알고리즘은 구현 후보에서 제외한다. Getty·MeSH·SKOS·DCMI는 관계 모델의 보충 참고 사례다.

프로젝트 분석은 로컬 소스와 use-case README, 완료 기록에 근거한다. 운영 DB나 실제 사용자별 Memory Tree는 조회하지 않았다. 따라서 실제 루트 개수, 중복률, 주제별 분포, 운영 placement 실패 횟수는 측정하지 않았으며, 본문의 가족 사례는 설명용 가상 사례다.

### 2.2 무엇이 확인되었고 무엇이 추론인가

| 판단 | 근거 수준 | 의미 |
|---|---|---|
| 신규 메모리가 다른 신규 메모리의 부모가 될 수 있다 | 코드·테스트로 확인 | 같은 batch의 다른 memory ID를 부모로 선택할 수 있다 |
| 현 placement는 입력에 없는 별도 상위 container를 합성하지 않는다 | 코드로 확인 | 부모 선택만 반환하며 새 container 사용을 금지한다 |
| 부모 역할을 맡아도 원래 content와 evidence는 보존된다 | 코드로 확인 | 직접 검색된 부모 내용은 답변 맥락에도 포함된다; 자식 검색 시 조상 추가는 별개다 |
| 현 저장 계약은 기존 다른 부모에서의 이동을 허용하지 않는다 | 코드로 확인 | `attachChildren`은 다른 부모가 있으면 거절한다 |
| 신규 추출은 원자 메모리 중심이다 | 코드로 확인 | 이후 부모 역할을 맡을 수 있지만, 누적 구조를 포괄하는 설명의 별도 합성은 없다 |
| 운영 화면의 파편화가 위 제약 때문에 발생했다 | 유력한 가설 | 실제 트리와 입력·실패 이력을 봐야 확정할 수 있다 |
| Memory와 교체 가능한 Topic을 분리한다 | 설계 전제 | 기존 관계 호환·migration 비용·외부 서비스 도입을 우선 고려하지 않는다 |
| 특정 그룹 크기나 정리 주기가 최적이다 | 미확인 | 실제 가족 기록과 사용 질문으로 검증해야 한다 |

메모리 개수가 많다는 사실만으로 품질이 낮다고 볼 수 없다. 여러 사실을 독립적으로 검색할 수 있게 만드는 것은 현재 시스템의 의도다. 문제는 사실의 수가 아니라, 사람이 이해하고 다시 찾을 수 있는 조직 구조가 그 증가를 따라가지 못하는 경우다.

## 3. ‘비슷한 메모리를 묶는다’에 포함된 서로 다른 작업

### 3.1 중복 제거와 주제 묶음은 다르다

| 관계 | 가상 사례 | 적절한 처리 |
|---|---|---|
| 같은 사실의 반복 | 같은 보일러 모델명이 두 기록에 등장 | 사실 정규화 검토, 각각의 근거 보존 |
| 같은 대상의 다른 사실 | 보일러 모델명, 설치일, AS 연락처 | 사실은 별도 유지, ‘보일러’ 주제 아래 연결 |
| 같은 영역의 다른 대상 | 보일러, 에어컨, 세탁기 정보 | ‘주택 설비’ 상위 주제 아래 하위 주제로 연결 |
| 관련은 있지만 포함 관계가 아님 | 보일러 수리와 겨울 생활비 | 당장 부모·자식으로 강제하지 않음 |
| 시간에 따른 상태 변화 | 이전 주소와 현재 주소 | 변경 이력 보존, 현재성 구분 |
| 사실로부터의 추론 | 여러 번 병원에 갔으니 만성 질환이라고 판단 | 확정 사실로 자동 저장하지 않음 |

같은 대상의 정보를 묶는 것과 같은 내용을 지우는 것은 별개다. “보일러 모델은 X다”와 “보일러 설치일은 Y다”를 하나의 사실로 합칠 이유는 없지만, 같은 주제 아래 놓을 이유는 있다. 날짜가 다른 수리 기록도 반복 문자열이 비슷하다고 중복으로 삭제해서는 안 된다.

### 3.2 상위 노드에는 세 가지 역할이 있다

첫째, 주제 노드는 “무엇에 관한 기억인가”를 나타낸다. 예를 들어 ‘보일러’는 검색과 탐색을 위한 안정적인 대상·영역이다. 이름, 범위 설명, 하위 주제와 연결된 메모리가 핵심이다.

둘째, 요약 노드는 “현재 기록에는 어떤 내용이 있는가”를 압축한다. 예를 들어 ‘보일러 설치·수리·보증 정보가 기록되어 있다’는 저장된 기억을 안내하는 설명이다. 하위 사실이 바뀌면 요약도 다시 생성해야 한다.

셋째, 추론 노드는 “여러 기록에서 어떤 패턴을 판단했는가”를 나타낸다. ‘이 설비는 고장이 반복된다’ 같은 판단은 적용 기간과 근거, 불확실성을 요구한다. 이를 단순 주제명이나 직접 발화된 사실과 같은 수준으로 취급하면 기억의 신뢰도가 흔들린다.

이 구분은 Hindsight가 사실, 경험, 종합된 엔티티 관찰, 의견을 분리하는 이유와 연결된다. 이 프로젝트에는 그 모든 계층이 필요한 것은 아니지만, 근거 사실과 파생 설명의 구분은 필요하다.[^8]

### 3.3 계층 추가, 병합, 재배치도 다르다

‘보일러’와 ‘에어컨’ 위에 ‘주택 설비’를 추가하는 것은 상위 주제 생성이다. ‘난방기’와 ‘보일러’가 실제로 같은 장비를 가리키는 것으로 확인되어 하나의 대표 주제로 정규화되는 것은 주제 병합이다. 이미 ‘생활비’ 아래 있던 보일러 보증 메모리를 ‘보일러’ 아래로 옮기는 것은 재배치다.

모든 문제에 상위 노드를 하나 더 만드는 방식은 권하지 않는다. 이름만 다른 동일 주제는 병합해야 하고, 불필요하게 깊은 계층은 축소해야 한다. 같은 영역이라는 이유로 너무 많은 사실을 담는 거대 주제는 오히려 분할해야 한다.

## 4. 기존 지식관리의 처리 방식

### 4.1 대표 이름, 별칭, 계층, 관련 관계

W3C SKOS는 개념의 대표 라벨과 대체 라벨, 더 넓은·좁은 개념 관계, 비계층적 관련 관계를 구분한다. 같은 개념은 여러 상위 개념에 연결될 수 있으며, 개념을 묶는 collection과 개념의 의미상 계층도 구분한다. 따라서 ‘이름이 다름’, ‘같은 주제임’, ‘관련이 있음’, ‘상위 개념임’을 동일하게 처리하지 않는다.[^1]

Obsidian의 별칭도 같은 노트를 여러 이름으로 참조할 수 있게 한다. 링크는 대표 노트를 향하고 표시 이름만 달라질 수 있다. 이 방식은 ‘AS’, ‘A/S’, ‘서비스센터’처럼 표현 차이 때문에 주제가 늘어나는 것을 줄이는 실용적인 사례다.[^13]

프로젝트에 적용할 핵심은 표준 전체를 구현하는 것이 아니다. 주제의 정체성을 제목 문자열과 분리하고, 비슷한 이름을 새 주제로 무조건 저장하지 않는 것이다. 다른 집의 서로 다른 보일러가 모두 ‘보일러’라고 쓰일 수 있으므로, 대상의 정체성과 범위도 함께 판단해야 한다.

### 4.2 트리는 보기 방식이지 모든 의미 관계의 정답은 아니다

가족 기록은 한 개의 엄밀한 분류 트리에 잘 들어맞지 않을 수 있다. 학교 비용은 자녀 교육과 가족 재정에 모두 관련되고, 이사 기록은 주소·계약·설비·생활 변화와 연결된다. 따라서 단일 부모 트리는 이해하기 쉬운 기본 탐색 경로로는 유용하지만, 다른 관점의 검색까지 막아서는 안 된다.

단일 기본 부모는 가능한 선택이지 현재 확정된 구조가 아니다. 단일 부모·복수 소속·관련 링크 중 무엇이 3.1의 관계를 가장 작고 명확하게 표현하는지 비교해야 한다. 다중 부모 그래프를 처음부터 도입해야 한다는 결론도, 기존 단일 부모를 반드시 유지해야 한다는 결론도 아니다.

## 5. LLM 기억·검색 시스템의 주요 접근

### 5.1 RAPTOR: 아래에서 위로 재귀적으로 묶고 요약

RAPTOR는 텍스트 조각을 임베딩하고 의미적으로 군집화한 뒤, 각 군집의 요약을 생성한다. 요약을 다시 임베딩·군집화·요약하면서 여러 추상화 수준의 구조를 만든다. 원문뿐 아니라 중간·상위 요약도 검색 대상으로 유지한다.[^3]

이는 “관련된 하위 기억을 상위 기억으로 다시 묶는다”에 대한 직접적인 선행 접근이다. 다만 원래 실험은 긴 문서 질의응답이며, 사람에게 안정적인 주제 이름을 제공하거나 가족 ACL을 보존하는 유지보수 시스템은 아니다. 또한 soft clustering을 사용하므로 이 프로젝트의 single-parent directory와 그대로 대응하지 않는다.

논문은 요약 환각 사례도 보고한다. 상위 요약이 있다고 해서 원문 검증이 불필요해지는 것이 아니다. 논문의 collapsed-tree 검색은 여러 계층을 동시에 검색하며, 트리가 존재한다고 루트부터 순서대로 내려가기만 해야 하는 것은 아니라는 점도 중요하다.[^3]

### 5.2 GraphRAG: 관계가 강한 엔티티들을 community로 묶음

Microsoft GraphRAG의 표준 흐름은 엔티티와 관계를 추출하고, Hierarchical Leiden으로 엔티티 community 계층을 만든 다음 community report를 생성한다. 넓은 질문은 community report, 구체적인 질문은 엔티티와 원문 맥락을 활용하는 식으로 질의 경로를 나눈다.[^4][^5]

단순히 같은 단어가 등장하는 메모리를 묶는 것보다 관계 구조를 활용하는 접근이다. ‘우리 집의 주거 관련 기록 전체’처럼 분산된 사실을 종합하는 질문에 참고 가치가 있다. 그러나 community는 자동 발견된 연결 집합이며 가족이 기대하는 안정적인 ‘보일러’, ‘학교’, ‘보험’ 폴더와 일치한다고 보장할 수 없다.

현 공식 문서는 incremental update 명령과 출력 구조도 제공한다. 그러므로 GraphRAG를 오직 전체 재구축만 가능한 방식으로 설명하는 것은 부정확하다. 다만 본 프로젝트에서는 외부 서비스·프레임워크를 도입하지 않으므로, 계층·요약 분리 원칙을 직접 구현할 설계 재료로만 참고한다.[^4][^14]

### 5.3 MemTree: 새로운 정보가 들어오면 기존 트리를 확장

MemTree는 새 정보와 기존 노드의 의미 유사도를 비교하며 트리를 내려간다. 유사한 기존 leaf에 도달하면 원래 내용을 자식으로 보존하고 새 정보와 함께 상위 노드 아래에 둔다. 삽입 경로의 상위 내용과 임베딩도 갱신한다. 더 깊은 위치에는 더 높은 유사도를 요구한다.[^6]

현재 placement도 신규 메모리를 부모로 삼아 상위 역할을 만들 수 있다. 차이는 상위 역할의 존재 자체가 아니라 내용과 구조의 갱신 방식이다. 현재 구현은 원래 leaf의 내용을 포괄적인 상위 설명으로 갱신하지 않는 반면, MemTree는 삽입에 따라 상위 표현도 갱신한다.

그렇지만 자동으로 학습된 트리의 깊이와 구조가 사람이 원하는 탐색 구조라는 보장은 없다. 삽입 경로마다 상위 요약을 갱신하는 비용도 생긴다. 따라서 ‘사실을 보존하며 상위 표현을 생성한다’는 요소를 채택하되 알고리즘 전체를 복제할 필요는 없다.

### 5.4 Mem0: 신규 사실을 기존 기억과 비교해 통합

Mem0는 신규 기억 후보에 대해 의미적으로 비슷한 기존 기억을 찾고, ADD·UPDATE·DELETE·NOOP 중 작업을 선택한다. 핵심은 기억을 무조건 추가하지 않고 기존 사실과의 관계를 판단하는 것이다.[^7]

하지만 이것은 주제 계층 재정리와 같은 문제가 아니다. 모델명 중복이나 같은 선호의 반복은 줄일 수 있어도 ‘보일러’와 ‘에어컨’ 위에 ‘주택 설비’를 만드는 문제를 그 자체로 해결하지는 않는다.

또한 논문의 DELETE/UPDATE를 가족 기억에 그대로 적용해서는 안 된다. 변경된 상태와 과거 상태는 모두 유용할 수 있고, 새로운 발화가 항상 더 정확하지도 않다. 이 프로젝트에서는 이전 증거를 삭제하는 통합보다 중복 사실의 대표화, 변경 이력, 현재성 표시를 별도 검토하는 것이 안전하다.

### 5.5 A-MEM: 원자 노트, 연결, 기존 기억의 의미 표현 개선

A-MEM은 Zettelkasten에서 영감을 받아 원자 노트에 문맥 설명·키워드·태그를 붙이고, 관련 기존 노트와 연결한다. 신규 기억은 기존 기억의 context·keywords·tags를 갱신하는 memory evolution도 유발할 수 있다.[^9]

이는 관련 사실이 꼭 하나의 부모 아래에만 있어야 한다는 가정을 완화한다. 그러나 연결을 많이 만드는 것과 상위 목록을 읽기 좋게 줄이는 것은 다르다. 현재 불편함이 루트 주제의 파편화라면, 링크와 태그만 추가해서는 충분하지 않을 수 있다.

이 프로젝트에서는 원자성 유지와 기존 조직 표현의 개선이라는 요소가 유용하다. 모든 기억에 다량의 모델 생성 메타데이터를 붙이는 방식은 추후 검색 이득과 유지 비용을 검증한 뒤 판단해야 한다.

### 5.6 Zep/Graphiti: 사실·시간·엔티티·community를 분리

Zep의 2025년 논문은 episode, semantic entity/fact, community 구조를 구분한다. 새로운 사실이 기존 관계와 충돌하면 시간 정보를 이용해 기존 관계의 유효성을 종료시켜 이력을 보존한다. 상위 community에는 엔티티 묶음의 요약이 들어간다.[^10]

특히 논문은 신규 엔티티를 이웃 community에 증분 배치하는 효율적인 방법과, 그 결과가 완전한 재계산에서 점점 벗어날 수 있어 주기적 community refresh가 필요하다는 점을 함께 설명한다. ‘넣을 때 대충 잘 배치하면 이후 정리는 필요 없다’는 가정에 대한 중요한 반례다.[^10]

현재 Graphiti 공식 MCP 구현에도 `build_communities`가 별도 기능으로 노출된다. 다만 논문의 시간·community 설계와 현재 특정 배포 버전의 설정·실행 조건은 구분해야 한다. `group_id` 같은 데이터 구획을 이 프로젝트의 PUBLIC/복수 사용자 ACL과 동일한 보안 모델이라고 가정해서도 안 된다.[^15]

### 5.7 Hindsight: 사실 위에 재생성 가능한 엔티티 종합을 유지

Hindsight는 원래 사실과 엔티티별 observation을 분리한다. Observation은 관련 사실을 종합한 설명이며, 기초 사실이 바뀌면 백그라운드에서 재생성한다. 의견과도 구분한다.[^8]

2026년 7월의 공식 구현 설명도 별도 백그라운드 consolidation과 근거 연결을 설명한다. 다만 논문의 재생성 설명과 달리, 현재 설명은 observation을 새 증거로 개선하고 이력을 보존하며 처음부터 다시 생성하지 않는다고 명시한다. 두 자료의 갱신 방식을 동일하게 가정하지 않는다.[^16]

주의할 점은 용어다. 현재 프로젝트의 `MemoryType.OBSERVATION`은 직접 기록된 관찰의 분류일 수 있지만, Hindsight의 observation은 여러 사실에서 합성한 엔티티 설명을 뜻한다. 이름이 같다고 같은 도메인 의미로 취급해서는 안 된다.

### 5.8 TiMem: 계층별 다른 통합 규칙과 실행 주기

TiMem은 segment·session·day·week·profile의 시간 계층을 사용한다. 세부 사실은 즉시 수집하고, 상위 계층은 시간 창이 닫힐 때 통합한다. 하위에는 사실, 상위에는 점진적으로 더 추상적인 패턴과 프로필을 둔다.[^11]

이 논문은 기억 파편화를 직접 문제로 제시한다. 그러나 가족의 설비·자산·규칙을 날짜 중심으로만 조직하면 오래 유효한 지식을 여러 주간 요약에 흩어 놓을 수 있다. 따라서 본 프로젝트에는 주제 중심 계층을 기본으로 하고, 사건의 시간은 사실 맥락으로 유지하는 편이 낫다.

채택할 요소는 ‘계층마다 다른 목적’과 ‘입력 즉시 수집, 상위 통합은 별도 수행’이다. 논문은 사용자별 격리된 트리를 가정하므로 가족 공유 ACL 검증의 대체 근거는 아니다.[^11]

### 5.9 xMemory: 상위 그룹의 파편화와 과대화를 함께 관리

xMemory는 재사용 가능한 사실·변경 단위를 먼저 분리한 후 그룹화한다. 이후 입력으로 기존 소속도 수정한다. 너무 넓은 그룹의 split과 작은 그룹의 merge를 명시한다.[^2]

현재 질문과 직접 맞닿는 연구다. 그러나 단일 구성원 그룹의 병합 규칙이나 수치 임계값을 가족 지식관리의 보편 규칙으로 채택할 근거는 아니다.

같은 논문의 LoCoMo/Qwen3-8B 실험에서 다음 결과를 보고한다.[^2]

| 구성 | 평균 F1 | 기존 component 재배치 비율 |
|---|---:|---:|
| split·merge 모두 제외 | 38.59 | 0.00% |
| split 제외 | 39.18 | 17.33% |
| merge 제외 | 40.33 | 26.23% |
| 전체 구조 유지보수 사용 | 43.98 | 44.91% |

이는 수정 가능한 구조를 지지하지만 가족 기록의 성능 보장은 아니다. 비교별 component 수도 같지 않다. 논문은 질의가 적으면 구축 비용 때문에 단순 검색이 더 적절할 수 있다고 밝힌다.[^2]

### 5.10 Letta: 실제 제품에서의 명시적 정리와 백그라운드 정리

확인 시점의 Letta 공식 문서는 기억 계층이 커지거나 흐트러졌을 때 placement·duplication·토큰 사용량을 진단하고, 큰 정리는 백업 후 파일 분할·중복 병합·계층 재구성을 수행한다고 설명한다. Dreaming은 활성 작업을 방해하지 않는 백그라운드 정리다.[^12]

실제 제품도 ‘좋은 기억 구조를 한 번 만들면 영원히 유지된다’고 보지 않는다는 사례다. 다만 현재 문서는 git-backed MemFS와 코딩 에이전트의 작업 기억에 관한 설명이다. 이를 가족 canonical memory 저장 모델이나 가족 구성원의 승인 workflow와 동일시하면 안 된다.

### 6.2 3.1의 관계 기준에서 무엇을 잘하고 무엇을 놓치는가

아래는 5번의 열 가지 접근법을 **같은 여섯 기준**으로 읽은 설계 비교다. 표가 너무 넓어지지 않도록 사실·주제 조직과 관련성·시간·추론으로 나누었다. 기존 6.1은 연구 개요이며, 이 표는 우리 문제의 어떤 부분에 답하는지를 보여 준다.

‘명시’는 해당 처리의 구조·연산을 자료에서 확인했다는 뜻이지 정확도나 가족용 적합성의 보장이 아니다. ‘부분’은 관련 기능이 있으나 기준 전체를 해결하지 못함, ‘공백’은 검토한 기본 설계의 주된 처리 대상이 아님, ‘미확인’은 자료로 판단하기 어려움을 뜻한다. 논문 간 실험 순위가 아니라 3.1을 적용한 분석이며, 공백을 시스템의 절대적인 구현 불가능으로 읽지 않는다.

| xMemory[^2] | 부분 — 정보 단위를 분리·집약; 출처별 근거를 가진 동일 사실 대표화는 별도 | 부분 — 분리한 단위를 그룹화; 특정 대상의 동일성은 별도 | 명시 — 그룹 split/merge·소속 수정; 사람이 정의한 broader 관계는 별도 |
| Letta[^12] | 부분 — 중복 병합·정리 기능; canonical 사실·근거 보존 계약은 미확인 | 부분 — 기억 파일 분할·배치; 원자 사실과 대상 모델은 별도 | 부분 — 계층 재구성은 지원하지만 주제 정체성·범위는 설계에 의존 |

#### 관련성, 시간 변화, 추론

| 접근 | 관련≠포함: 부모로 강제하지 않음 | 시간 변화: 과거 보존·현재성 구분 | 추론≠사실: 근거·불확실성 구분 |
|---|---|---|---|
| RAPTOR[^3] | 부분 — soft clustering으로 복수 군집 가능; 관련 관계의 명시적 의미는 없음 | 공백 — 요약 계층 자체에는 상태 유효기간 계약이 없음 | 부분 — 원문·요약은 분리; 요약에서 생긴 추론의 확실성 검증은 별도 |
| GraphRAG[^4][^5] | 명시 — 엔티티 관계를 계층과 별도로 표현 | 부분 — 선택적 claim의 시간 정보; 일반 사실의 과거/현재 lifecycle과는 다름 | 부분 — 원문·파생 report 분리; 추론의 사실 승격 방지는 별도 |
| MemTree[^6] | 공백 — 기본 표현은 트리; 임의 관련 링크는 별도 | 부분 — 시간 맥락을 담을 수 있으나 상태 유효성·이력 계약은 별도 | 부분 — 원본 leaf·상위 집약을 구분; 추론의 타입·불확실성은 별도 |
| Mem0[^7] | 공백 — 기본 Mem0 사실 갱신 비교; 별도 graph 변형과 구분 | 부분 — 새 상태로 갱신 가능; DELETE/UPDATE 이후 과거 보존은 보장하지 않음 | 공백 — ADD/UPDATE 판단 자체가 독립 추론 타입을 제공하지 않음 |
| A-MEM[^9] | 명시 — 노트 간 유연한 관련 링크; 하나의 부모로 강제하지 않음 | 부분 — timestamp·기억 진화; 상태의 현재성/종료는 별도 | 부분 — 원래 내용·생성 속성 분리; 암묵적 해석의 사실화 방지는 별도 |
| Zep/Graphiti[^10] | 명시 — 엔티티 관계와 community를 별도로 표현 | 명시 — 관계의 유효·종료 시점으로 과거 관계를 보존 | 부분 — episode·추출 사실·요약은 구분; 독립 의견과 확실성 계약은 별도 |
| Hindsight[^8][^16] | 명시 — 엔티티·의미·시간 등 여러 연결; 단일 포함 트리가 아님 | 부분 — 시간 기반 사실·종합 갱신; 모든 상태의 현재성 판정은 별도 | 명시 — 사실·종합 observation·의견을 구분하고 근거 연결; 추론의 진실 보장은 아님 |
| TiMem[^11] | 공백 — 기본 조직은 시간적 포함 트리 | 부분 — 시간 계층·원본 보존은 강점; ‘현재 주소’의 유효성은 별도 | 부분 — 세부 사실·상위 패턴/프로필을 나눔; 추론을 확정하지 않는 계약은 별도 |
| xMemory[^2] | 부분 — 근접성 기반 연결·그룹 조정; 관련/포함의 의미 타입은 별도 | 부분 — 변화 단위를 분리; 유효·종료 시점 기반 상태 모델은 별도 | 부분 — 기초 단위·집약 표현 분리; 독립 추론 타입·불확실성은 별도 |
| Letta[^12] | 미확인 — 파일 재조직 설명만으로 관계 모델을 확정할 수 없음 | 미확인 — 검토 문서에는 상태 유효기간·이력 모델의 명시가 없음 | 미확인 — 파일과 정리 절차만으로 사실/추론 계약을 확정할 수 없음 |

이 비교에서 도출되는 판단은 ‘하나를 고르면 여섯 관계가 모두 해결된다’가 아니다. **주제 재구성에는 xMemory·MemTree, 비계층 관련성에는 A-MEM·그래프 접근, 시간 이력에는 Zep, 사실과 파생 판단의 구분에는 Hindsight**가 특히 유용한 설계 재료다. 그러나 우리 시스템에서는 이 기능들이 같은 Memory를 서로 다르게 변형하지 않도록 먼저 객체 경계를 분리해야 한다.

또한 ‘그룹이 만들어진다’와 ‘Memory와 독립적으로 Topic 구조를 갈아끼울 수 있다’는 다르다. 트리·community·파일 계층을 제공한다는 사실만으로 교체 가능한 Topic 계약을 충족했다고 판단할 수 없다. 8번에서는 그 경계를 먼저 정의한다.

### 6.3 공통된 설계 방향

관찰되는 방향은 원래 정보와 조직·압축 표현을 구분하고, 새 입력만 배치하는 것에 그치지 않으며, 질의에 필요한 세부 근거로 돌아갈 경로를 유지하는 것이다. 특히 상위 주제는 생성 이후에도 수정·통합·분할될 수 있는 대상으로 보는 편이 타당하다.

그러나 모든 시스템이 같은 consolidation을 구현하는 것은 아니다. Mem0의 사실 갱신, RAPTOR의 군집 요약, A-MEM의 메타데이터 진화, xMemory의 그룹 재구성은 서로 다른 작업이다. ‘메모리 통합 기능’ 하나로 부르면 설계 범위가 불명확해진다.

### 6.4 벤치마크 점수로 제품을 고르면 안 되는 이유

긴 문서 QA, 다회차 대화, 개인 선호 기억은 가족 공유 기록과 다르다. 모델, 평가 질문, retrieval budget, judge, prompt가 다르면 논문들의 정확도를 한 표에 세워 시스템 순위를 만들 수 없다. 한국어·카카오 기록·복수 사용자 권한·설비와 자산의 장기 이력은 별도로 검증해야 한다.

LongMemEval은 정보 추출, 여러 세션의 종합, 시간 추론, 지식 갱신, 모름 판단을 구분해서 평가한다. 이 분류는 자체 평가 질문을 만들 때 유용하지만, 사람이 읽기 좋은 상위 계층이나 가족 ACL까지 검증해 주지는 않는다.[^17]

### 6.5 증분 배치와 주기적 재정리는 양자택일이 아니다

매 입력마다 전체 기억을 재조직하면 비용과 구조 변동이 크다. 반대로 입력 때만 기존 주제에 붙이면 초기에 잘못된 경계나 여러 표현으로 나뉜 주제가 고착될 수 있다. Zep의 community refresh와 xMemory의 드문 split/merge는 이 중간 지점을 보여 준다.[^2][^10]

adRAP도 동적 데이터에서 recursive-abstractive 구조를 효율적으로 갱신하기 위한 별도 알고리즘을 제안한다. 변경된 군집과 상위 요약을 갱신하는 것은 기존 구조에 새 leaf를 붙이는 것보다 큰 책임이다. 처음부터 그 알고리즘을 도입할 필요는 없지만, ‘상위 설명도 데이터 변화에 따라 유지보수해야 한다’는 점을 뒷받침한다.[^18]

## 7. 현재 프로젝트 구조의 분석

### 7.1 원자 사실과 상위 설명의 의미가 겹쳐 있다

`Memory`의 주석은 자식이 있는 메모리를 지식 영역의 짧은 설명, 자식이 없는 메모리를 원자 사실이라고 정의한다. 반면 추출은 flat atomic memory를 만든다. 자식을 붙여도 부모의 content를 영역 설명으로 바꾸거나 원래 사실을 별도 leaf로 옮기지는 않는다. 따라서 원자 사실과 주제가 한 객체에서 역할을 겸할 수 있다는 문제는 실제 계약의 불일치다.[^L1][^L3][^L4]

예를 들어 ‘보일러 모델은 X다’ 아래 설치일·수리기록을 붙여도 부모 내용은 그대로다. 그 사실이 ‘보일러 관련 정보’ 폴더를 겸한다고 해서 포괄적인 주제 설명이 되는 것은 아니다.

다만 **부모가 되면 원래 정보를 가져오지 않아 무시한다는 가설은 현재 코드에서 확인되지 않았다.**

| 경로 | 확인된 동작 | 의미 |
|---|---|---|
| 관계 저장 | `childrenIds`·수정 시각만 변경; content·evidence 유지 | 부모 전환 시 원래 사실을 삭제하지 않음 |
| 인덱싱·직접 검색 | 모든 Memory의 subject/content를 인덱싱하고 검색된 ID의 canonical content를 반환 | 자식 보유 여부만으로 부모 사실을 제외하지 않음 |
| 답변 맥락 | 직접 검색된 Memory를 유지하고 일부 자식을 추가; 각 match의 content 전달 | 부모가 직접 검색되면 원래 내용도 전달됨 |
| 자식에서 부모로 확장 | 조상을 자동 추가하는 경로는 없음 | 자식만 검색되면 부모의 사실이 함께 오리라는 보장은 없음 |

저장·검색·답변 동작은 각각 repository, index writer/searcher, answer/conversation context에서 확인했다.[^L3][^L7][^L12] 2026-08-08 단순화 기록의 ‘배치 후 부모 재인덱싱 제거’도 부모 content가 변하지 않고 관계 payload를 검색에서 쓰지 않기 때문이지, 부모 사실을 제외하기 위한 변경은 아니다.[^L10]

대화 맥락 전체에는 8,000자 제한이 있어 일부 내용이 잘릴 수 있으나 이는 부모에만 적용되는 제외 규칙이 아니다.[^L12] 실제 특정 정보가 누락됐는지는 당시 검색 결과와 맥락을 봐야 한다. 현재의 핵심 설계 문제는 확인되지 않은 정보 폐기가 아니라 **사실 객체와 조직 객체의 역할 혼합**이다.

### 7.2 신규 상위 역할은 가능하지만 누적 구조의 consolidation은 아니다

`MemoryPlacementService`는 입력 batch를 기존 visible memory에서 제외하고, 기존 트리 일부를 모델에 보여 준 뒤 각 신규 memory의 parent를 선택한다. 기존 표시 노드 또는 같은 batch의 다른 memory만 선택할 수 있으며, 적절한 부모가 없으면 root로 둔다.[^L2]

즉 같은 batch에서 새로 저장된 `101`을 신규 `100`의 부모로 선택하면, 새 메모리 `101`은 상위 역할을 맡는다. 실제 회귀 테스트도 기존 root `1` 아래 신규 `101`, 그 아래 신규 `100`을 붙이는 사례를 포함한다. 상위 메모리가 만들어지거나 늘어날 수 있다는 점은 현재 기능의 일부다.[^L2]

기본 노출 깊이는 2다. 이는 깊이가 지나치게 늘어나는 것을 피하려고 선택한 입력 구조다. 루트 기준 깊이 0·1·2까지만 기존 부모 후보로 보이므로 깊이 3 이상의 적절한 주제는 선택할 수 없을 수 있다.[^L2]

다만 **부모 후보의 노출 깊이 제한과 결과 트리의 최대 깊이 제한은 다르다.** 깊이 2의 후보 아래 신규 memory를 붙이거나 같은 batch의 신규 부모 사슬을 연결할 수 있으므로, 후보 제한만으로 저장 결과를 깊이 2에 묶지는 않는다. 새 구조에서는 화면·모델 입력·저장 계층의 깊이 정책을 각각 판단해야 한다. 단순히 제한을 풀어 더 깊게 쌓는 것이 결론은 아니다.

프롬프트 문구를 개선하면 신규 기억을 기존 부모 또는 같은 batch의 신규 부모에 더 잘 붙이는 데 도움은 될 수 있다. 그러나 적절한 부모가 후보 목록에 없을 때 별도의 상위 메모리를 합성하거나, 이미 누적된 상위 메모리들을 다시 통합·정규화하는 작업은 현 응답 계약 밖이다. 문제의 초점은 ‘상위 메모리 생성 부재’가 아니라 ‘상위 역할 형성 이후의 재정리 과정 부재’다.

### 7.3 저장 계층은 기존 부모 변경을 거절한다

`MemoryRepository.attachChildren`은 동일 child가 다른 visible parent에 있으면 요청을 거절한다. 최종 그래프 cycle도 검증하고 transaction 안에서 관계를 저장한다. 이는 신규 배치의 안전성에는 좋지만, 기존 주제 병합에서 필요한 여러 child의 재배치 계약은 아니다.[^L3]

기존 루트 몇 개를 이미 저장된 더 넓은 memory 아래에 붙이는 제한적인 정리는 가능할 수 있다. 하지만 누적된 기억을 포괄하는 별도 상위 설명의 합성, 기존 parent 해제와 새 parent 연결, 병합된 주제의 대표화, 내용 갱신은 각각 추가 설계가 필요하다. 신규 batch 메모리가 부모가 되는 기존 기능과는 구분해야 한다.

### 7.4 bootstrap 재실행은 정리 기능의 대체가 아니다

`MemoryTreeBootstrapService.placeExistingRoots`의 이름과 주석은 flat root 대상이지만, 실제 구현은 visible memories 전체에서 `take(limit)`한다. 루트 조건을 필터링하지 않는다. 따라서 중첩 구조가 있는 데이터에 그대로 재사용하면 이미 다른 부모가 있는 memory도 대상으로 들어갈 수 있다.[^L5]

이는 이번 조사에서 발견한 재사용 제약이다. bootstrap을 반복 실행하거나 limit을 키우는 방식은 누적된 상위 메모리의 통합·재정리를 대체하지 않으며, 기존 구조에서 저장 검증 실패를 유발할 가능성도 있다. 이번 보고서에서는 코드를 수정하지 않는다.

### 7.5 ACL에 따른 사용자별 root는 정상 동작이다

조회 projector는 사용자가 볼 수 있는 memory만으로 forest를 만든다. visible parent가 없으면 그 memory는 root로 표시된다. cycle이나 root에서 도달할 수 없는 legacy component도 별도 root로 보여 주며 저장 관계는 수정하지 않는다.[^L6]

그러므로 한 사용자 화면의 root 수는 전역 저장 구조의 root 수와 같지 않다. 비공개 부모를 숨겨야 해서 공개 child가 root로 보이는 경우는 정상 동작이며, 이번 구조 개선에서 고쳐야 할 결함이 아니다. 루트 수를 줄이기 위해 숨겨진 부모명이나 비공개 내용을 공개해서는 안 된다.

### 7.6 깊은 계층은 현재 답변 맥락 확장과도 맞지 않을 수 있다

현재 답변 context provider는 직접 검색된 memory의 자식만 깊이 1로 확장한다. seed마다 visible child 후보는 저장 순서상 최대 5개이며, 재검색 후 seed당 최대 1개, 전체 최대 2개를 추가한다. 손자까지 재귀적으로 내려가지 않는다.[^L7]

새로운 구조가 ‘주택 설비 → 보일러 → 수리·보증 사실’이라면 ‘주택 설비’가 seed일 때 상세 사실이 자동 확장된다고 보장할 수 없다. 많은 child를 가진 주제에서는 후보 제한 밖의 사실도 빠질 수 있다. 다만 상세 사실은 여전히 직접 검색으로 찾을 수 있으므로, 계층 추가가 언제나 검색 실패를 만든다는 뜻은 아니다.

결론적으로 탐색 구조와 검색 전략은 함께 평가해야 한다. 화면만 예쁘게 정리하고 원자 사실 검색을 상위 요약으로 대체하는 변경은 피해야 한다.

### 7.7 중복 요청 방지와 의미 중복 제거는 다르다

현 idempotency key에는 작성자, 의미 필드, 정렬된 evidence ID 집합이 들어간다. 같은 처리의 재시도 중복을 막는 장치이며, 다른 source가 같은 사실을 다시 말한 모든 경우를 하나의 대표 기억으로 정규화하는 기능은 아니다.[^L8]

따라서 반복 입력에서 동일 사실 메모리가 늘어나는 문제와, 관련된 다른 사실 또는 상위 역할의 메모리들이 여러 갈래로 파편화되는 문제를 분리해 측정해야 한다. 이번 불편함은 후자의 문제 제기에 해당하지만, 실제 데이터 없이는 중복 주제·상위 주제 부재·잘못된 부모·ACL 투영의 비율을 확정할 수 없다.

## 8. 권장 도메인 모델

### 8.1 Canonical Memory까지는 기반, Topic부터는 교체 가능한 구조

현재 유용한 기반은 원래 입력과 근거를 가진 **SourceRecord → Canonical Memory**까지로 본다. 기존 부모·자식 Memory 관계가 이미 있다는 구현 사실과, 그 관계를 새 설계의 Topic 모델로 인정하는 것은 별개다. 기존 관계를 해체해 flat memory로 돌아가거나 작은 데이터를 다시 구성할 수 있으므로, 지금은 그 관계 보존에 설계를 맞추지 않는다.

권장 논리 구조는 다음과 같다. 저장 스키마 확정안이 아니라 객체와 관계의 책임을 나타낸다.

```text
SourceRecord ← evidence ─ Canonical Memory
                              ↑ membership
                            Topic
                              ↑ broader / parent
                            Topic

선택적 Topic Summary ─ supporting Memory → Canonical Memory
```

**Topic–Broader Topic은 새로운 종류의 객체 두 개가 아니라, 동일한 Topic 객체 사이의 상위 관계다.** 계층 모양은 기존 Memory–Parent Memory와 같을 수 있다. 달라져야 할 것은 노드의 정체성이다. 원자 사실 대신 대상·지식 영역을 나타내는 Topic끼리 관계를 맺는다.

| 객체·관계 | 책임 | Topic 구조를 교체할 때 |
|---|---|---|
| Canonical Memory | 사실·규칙·사건·결정과 근거·시간·확실성·ACL | 그대로 보존; Topic 부모나 자식 역할을 맡지 않음 |
| Topic | 대상·영역의 대표 이름과 범위 | 필요하면 새로 만들고 합치거나 나눔 |
| Topic–Memory 소속 | 어떤 주제에서 어떤 기억을 찾는가 | 다시 계산·연결; Memory를 복제하거나 수정하지 않음 |
| Topic–Topic 상위 관계 | 주제의 더 넓은 탐색 영역 | 재배치하거나 전체 구조를 교체 |
| 선택적 요약 | 해당 구조의 사실 안내·압축 표현 | 근거를 유지하며 재생성; Canonical Memory로 자동 승격하지 않음 |

Topic의 최소 후보 정보는 ID, 대표 이름, scope description, 구성원 연결이다. 상위 관계가 필요하면 Topic끼리 연결한다. 단일 부모인지 다중 부모인지, 같은 Memory의 복수 소속을 허용할지, 관련 링크를 추가할지는 아직 열린 선택이다. 이전 single-parent Memory tree를 그대로 가져와 확정하지 않는다.

Topic 아래 Memory가 하나만 있어도 Topic은 Topic이다. 마지막 소속이 사라지거나 상위 관계가 바뀌어도 원자 사실로 바뀌지 않는다. 반대로 Memory가 어떤 주제에 속하더라도 내용과 근거는 그 Memory에 남는다.

### 8.2 migration 비용이 아니라 객체 분리가 선택 기준이다

기존 데이터가 적고 새로 구성할 수 있으므로 **migration 비용은 없는 것으로 가정**한다. 또한 외부 기억 서비스·GraphRAG/Graphiti 서비스·범용 프레임워크 도입은 선택지에서 제외한다. 학습 가치와 구조를 직접 이해하고 바꿀 수 있는 통제권을 위해, 기존 애플리케이션 내부에서 구현한다.

| 내부 모델 선택 | 잘하는 것 | 핵심 문제 | 현재 판단 |
|---|---|---|---|
| Memory가 사실·container를 계속 겸함 | 기존 관계 표현 재사용 | 주제 재구성이 사실 객체의 역할을 바꿈 | 핵심 요구에 맞지 않음 |
| 공통 저장 구조에서 서로 다른 Memory·Topic 객체를 구분 | 같은 DB·일부 저장 코드 공유 가능 | role 필드만 붙이고 동일 계약으로 다루면 역할 혼합이 재발 | 논리 객체·생명주기가 실제 분리될 때만 대안 |
| 별도 Topic·소속·상위 관계 모델 | Memory는 축적, Topic 구조는 독립 재구성 | 소속과 상위 관계의 의미를 정해야 함 | 우선 탐색할 가장 명확한 모델 |

Memory와 Topic은 단순한 화면 분류가 아니라 서로 다른 도메인 객체다. Memory 수집은 특정 Topic 트리가 있어야 성공하는 흐름이 아니며, Topic 삭제·재생성은 근거 사실을 삭제하는 연산이 아니다.

여기서 ‘별도 모델’은 별도 서버나 별도 DB 제품을 뜻하지 않는다. 도메인 객체의 분리와 물리 저장 방식은 다른 결정이다. Memory의 근거·ACL·사실 저장 책임과 Topic의 조직 책임을 나누면, 기존 DB에서도 구현할 수 있다.

기존 Memory–Parent Memory 관계는 두 방식으로 취급할 수 있다. 첫째, 버리고 Canonical Memory에서 Topic 구조를 새로 만든다. 둘째, 유용한 연결만 조직의 초안으로 참고하고 실제 사실 내용은 Memory에 남긴다. 두 번째는 관계 모양을 재사용하는 선택일 뿐, 기존 부모 Memory 자체를 그대로 Topic으로 바꿔 원래 사실을 잃는 변환이 아니다.

객체가 잘 분리되면 제한적인 migration도 가능할 수 있다. 그러나 여기서는 그것을 우선 과제로 삼지 않는다. 데이터 재구성은 설계의 허용 전제이며, 실제 관계 해체나 DB 삭제를 수행했다는 뜻은 아니다.

### 8.3 지금의 canonical writer를 억지로 재사용하면 안 되는 이유

현재 `Memory`는 비어 있지 않은 evidence를 요구한다. Canonical batch writer도 evidence가 현재 분석 대상 source batch에 속하는지 검증한다. 이미 저장된 여러 memory에서 만든 파생 주제를 신규 source 추출처럼 저장하려면 이 계약을 우회하거나 의미를 변형하게 될 수 있다.[^L3][^L4]

주제의 구성원 연결과 요약의 근거는 `supportingMemoryIds` 같은 파생 provenance로 구분하는 편이 명확하다. 구체 요약 문장은 실제로 지지하는 memory와 연결되어야 한다. 모든 descendant의 source evidence를 하나로 합쳐 붙이면 어떤 출처가 어떤 요약 주장을 뒷받침하는지 불명확해질 수 있다.

주제 생성용 가짜 SourceRecord, 빈 evidence 허용, `REFERENCE`나 `OBSERVATION` type으로의 임의 위장은 권하지 않는다. 도메인 계약을 명시적으로 새로 정의하는 것이 학습과 복구 측면에서도 이해하기 쉽다.

## 9. 구체적인 재정리 과정

### 9.1 후보는 유사도로 찾고 관계는 별도로 판단

지금처럼 데이터가 적은 단계에서는 Canonical Memory 전체에서 Topic 구조를 새로 만드는 실험도 가능하다. Topic이 생긴 이후에는 비슷한 루트·형제 주제와 미분류 Memory의 작은 집합을 국소 재정리할 수 있다. 메모리가 적으면 같은 ACL 범위의 제목·내용을 제한된 한 묶음으로 검토하는 것부터 충분하다. 규모가 커지면 기존 embedding 검색으로 인접 후보만 가져오는 방식이 적절하다.

임베딩 점수는 후보 생성에만 사용한다. 같은 대상인지, 더 넓은 주제인지, 같은 영역의 다른 사실인지, 시간 변경인지, 단지 관련만 있는지 따로 판단해야 한다. 높은 cosine similarity를 내용 병합 승인으로 사용하지 않는다.

### 9.2 Topic에 대한 작업과 Memory 소속을 구분

최소 proposal은 다음 작업을 구분할 수 있다.

- `CREATE_TOPIC`: 여러 기억을 포괄하는 새 주제 생성.
- `LINK_MEMORY`: Topic에 기존 Memory를 연결; 사실 내용은 바꾸지 않음.
- `LINK_TOPIC`: 하위 Topic과 상위 Topic을 연결; Memory 소속과 다른 관계.
- `MERGE_TOPICS`: 같은 정체성·범위의 주제를 대표 주제로 통합.
- `REPARENT`: Topic 간 기존 상위 연결을 해제하고 새 상위 Topic으로 이동.
- `SPLIT_TOPIC`: 너무 넓은 주제를 실제 하위 영역으로 분리.
- `NOOP`: 관련이 약하거나 정리 이득이 없으면 유지.

처음부터 이 모든 작업을 구현해야 하는 것은 아니다. 첫 지속 저장 버전은 `CREATE_TOPIC`과 `LINK_MEMORY`로 시작하고, 실제 필요가 있는 작업부터 확장할 수 있다. 다만 기존 부모 변경이 필요한 경우 이를 `attach`라고 숨겨 표현해서는 안 된다.

여기서는 필요한 관계를 표현하는 작업 이름만 구분한다. 기대 상태·원자적 적용·재시도 등 운영 계약은 구조를 정한 다음 설계한다. Topic 재정리와 같은 사실의 정규화·시간 변경 처리는 서로 다른 작업이다.

### 9.3 병합·상위화의 판단 기준

좋은 상위 주제는 가족이 다음 질문을 할 때 다시 사용할 수 있어야 한다. 구성원들이 같은 대상 또는 안정적인 지식 영역에 속해야 하고, 제목은 짧되 무엇을 포함하는지 범위가 명확해야 한다. 이미 같은 영역을 대표하는 주제가 있으면 새로 만들기보다 재사용한다.

여러 memory가 있다는 이유만으로 상위 주제를 만들지 않는다. ‘올해의 여러 가지 일’, ‘최근 대화’, ‘가족 관련 정보’ 같은 입력 시점·대화 단위 그룹은 영속 지식의 탐색 기준으로 약할 수 있다. 반대로 memory가 한 개뿐인 ‘집 보험’도 앞으로 다시 찾을 독립 대상이라면 유지할 이유가 있다.

그룹 크기는 진단 신호이지 강제 규칙이 아니다. 너무 작고 비슷한 주제가 여럿이면 병합 후보이며, 너무 넓어 관련성이 낮은 구성원이 많으면 분할 후보다. 연구의 특정 threshold나 ‘상위 주제 10개’ 같은 숫자를 실측 없이 제품 규칙으로 채택하지 않는다.

### 9.4 가상 예시

```text
정리 전
├─ 보일러 모델
├─ 난방 수리 연락처
├─ 보일러 보증 기간
├─ 에어컨 설치
└─ 세탁기 누수 대처

정리 후의 탐색 projection
└─ 주택 설비
   ├─ 보일러
   │  ├─ 모델 정보          기존 Memory ID 유지
   │  ├─ 수리 연락처       실제로 같은 설비인 경우만 연결
   │  └─ 보증 기간
   ├─ 에어컨
   │  └─ 설치 정보
   └─ 세탁기
      └─ 누수 대처
```

기존 사실의 내용과 evidence는 그대로다. 상위 주제 생성과 구성원 연결만 달라진다. 실제 기록이 다른 집의 설비, 이전 장비, 다른 열람 범위를 포함한다면 위 구조를 그대로 적용하지 않는다.

## 10. 지금 결정할 구조와 검증 질문

현재 단계의 목표는 운영 자동화나 rollout 순서를 정하는 것이 아니라, Memory를 축적하면서 Topic 구조를 바꿀 수 있는 경계를 정하는 것이다.

### 10.1 설계의 전제

| 항목 | 현재 전제 | 아직 확정하지 않은 것 |
|---|---|---|
| 사실 저장 | SourceRecord·Canonical Memory를 기반으로 삼는다 | 서로 다른 출처의 같은 사실을 대표화하는 규칙 |
| 조직 객체 | Memory와 Topic을 분리한다 | Topic의 식별·범위·소속 판단 방식 |
| 상위 관계 | Topic과 더 넓은 Topic 사이의 관계다 | 단일 부모, 다중 부모, 관련 링크의 허용 범위 |
| 구조 변경 | Topic 구조만 다시 만들 수 있어야 한다 | 전체 재생성, 국소 수정, 두 방식의 조합 |
| 기존 데이터 | 적고 재구성이 가능하므로 migration 비용을 제약으로 두지 않는다 | 기존 연결을 참고할 가치가 있는지 |
| 구현 환경 | 기존 애플리케이션 안에서 직접 구현한다 | 최소 저장·조회 표현; 별도 외부 서비스 도입은 제외 |

### 10.2 구조 선택 전에 답할 질문

1. ‘보일러’는 특정 장비인가, 모든 보일러에 관한 영역인가? 장비 교체나 다른 집의 기록이 같은 제목 때문에 섞이지 않는가?
2. 한 Memory가 ‘보일러’와 ‘주거 비용’ 양쪽에서 유용할 때 복제하지 않고 두 탐색 관점을 표현할 수 있는가?
3. Topic 트리를 완전히 폐기하고 다른 구조로 다시 만들었을 때 Memory의 내용·ID·근거·시간·확실성·ACL이 그대로인가?
4. Topic을 병합·분할했을 때 같은 사실을 합치거나 삭제하지 않고 조직만 달라지는가?
5. 요약과 추론을 생략해도 제목·범위·소속만으로 구조를 설명할 수 있는가? 추가한다면 사실 저장과 구별되는가?
6. 깊이 제한은 탐색 화면의 제한인가, 저장 관계의 제한인가, 배치 모델의 입력 제한인가? 셋을 혼동하지 않는가?

이 질문들은 특정 연구의 성능 점수 대신, 3.1의 서로 다른 관계를 설계가 제대로 표현하는지 검증한다. 11번은 그 구조를 오래 유지하기 위한 링크 모델과 수치적 판단을 구체화한다. 기존 운영 세부사항과 구현 단계안은 [별도 운영 참고](memory-consolidation-operations-notes.md)에 분리했다. 그 내용은 이후 검토할 참고안이며 현재 구조나 구현 순서를 확정하지 않는다.

## 11. 기존 1–18번 자료의 링크·배치·재정리 기준

### 11.1 범위와 직접 답변

**기존 자료 안에 있었다.** 신규 배치의 수치 기준은 MemTree와 xMemory에, 비계층 링크는 A-MEM·xMemory·Hindsight·Zep에, 구조 수정의 조건과 후보 비교는 특히 xMemory에 명시되어 있다. 다만 ‘장기간 사용하면 전체 지식 구조를 언제 재구축해야 하는가’에 대한 보편적인 품질 임계값까지 갖추었다고 볼 수는 없다.

이 프로젝트에서는 고전 군집 알고리즘을 채택하지 않는다. 따라서 기존 논문을 읽을 때도 **전체 재학습·재군집화 없이 참고할 수 있는 배치 규칙, 링크 생성, 국소 수정의 판단**과 **군집 알고리즘 자체**를 구분한다. RAPTOR·GraphRAG·adRAP은 연구 비교 자료로 남지만, 그 군집 파이프라인을 구현 후보로 삼지 않는다. xMemory 역시 분할 단계에는 국소 군집화가 있으므로 전체 알고리즘을 그대로 채택하는 후보는 아니다.

이 절은 기존 1–18번 자료를 다시 읽은 결과다. 뒤의 Getty·MeSH·DCMI 등 보충 자료는 관계 모델의 참고 사례일 뿐, 이 질문의 수치적 답변 근거로 사용하지 않는다. 앞서 제안한 Topic 반경·silhouette·ARI·ADWIN 중심의 설명은 이 절에서 제외한다.

### 11.2 어떤 논문에 무엇이 실제로 있는가

| 기존 자료 | 신규 root/sub 또는 기존 묶음 배치 | 계층 밖 링크 | 재정리 조건·수치 | 고전 군집 제외 관점 |
|---|---|---|---|---|
| MemTree[^6] | cosine과 깊이별 threshold 비교; 통과하면 하강, 아니면 현재 노드에 새 자식 | 기본 모델은 Tree | 삽입 경로의 상위 표현 갱신; 별도 전체 재구축 품질 threshold는 확인되지 않음 | 온라인 삽입 규칙 참고 가능; 논문 자체도 온라인 계층 군집과 연결됨 |
| xMemory[^2] | 가장 가까운 그룹과 cosine > 0.6이면 attach, 아니면 새 그룹 | group/component 사이 kNN; k=10 | 크기 cap 12, split·merge 기준 0.65, 목적함수 개선량 | 배치·링크·수정 판단은 참고; split의 국소 군집화는 채택 대상에서 제외 |
| A-MEM[^9] | 원자 노트 저장 후 관련 후보 검색; root/sub 분류 모델은 아님 | cosine top-k 후보를 LLM이 검토해 링크 생성 | 신규 입력 때 이웃 노트의 context·keywords·tags 개선; 재구축 품질 cutoff는 확인되지 않음 | 군집 재학습 대신 후보 검색+LLM 관계 판단 참고 |
| Zep[^10] | 신규 엔티티는 이웃 중 가장 많은 이웃이 속한 community로 배치 | 엔티티 관계와 community 소속을 분리 | 증분 결과가 완전 실행 결과에서 벗어나므로 주기적 refresh 필요; 발동할 품질 수치는 제시하지 않음 | label propagation 자체는 채택 제외; 증분 갱신의 한계는 참고 |
| Hindsight[^8][^16] | 사실·엔티티 종합 중심; Topic root/sub 기준은 아님 | entity·temporal·semantic·causal 링크; semantic은 cosine ≥ θs | 관련 사실 변화 후 observation 갱신; 전체 Topic 재구축 기준은 아님 | 링크 의미·수치와 사실/파생 정보 경계 참고 |
| TiMem[^11] | 시간 구간에 따라 segment/session/day/week/profile 소속 | 기본 모델은 시간 Tree | 시간 창이 닫히면 상위 통합; 구조 악화를 측정한 trigger가 아님 | 군집화 없이 통합 가능하나 주제 계층 문제의 직접 답은 아님 |
| adRAP[^18] | GMM posterior > 0.1인 군집에 배치 | 기본 조직은 recursive-abstractive 구조 | 크기 τc 초과 시 split 후보, BIC 비교; τn으로 근사/full EM 분기 | UMAP/GMM에 의존하므로 채택 제외 |

1–18번 중 나머지는 다른 질문에 답한다. SKOS·Obsidian은 관계/이름 구분, Mem0는 사실 ADD/UPDATE/DELETE/NOOP, GraphRAG 문서는 community·검색·update, Letta는 진단·dreaming 실행, LongMemEval은 기억 활용 능력 평가다. 이 자료의 관련 기능을 ‘root/sub 자동 판정 및 품질 기반 재구축 threshold’로 바꾸어 읽지 않는다.[^1][^4][^5][^7][^12][^13][^14][^15][^17]

### 11.3 MemTree: 깊이에 따른 온라인 배치 임계값

현재 노드의 자식들과 신규 입력의 cosine을 비교한다. threshold를 넘는 자식 중 최고 점수의 경로로 내려가고, 모두 미달이면 현재 노드에 새 leaf를 붙인다. 구조용 root에서 모두 미달이면 새 최상위 가지가 된다. 기존 leaf까지 내려가면 원래 leaf와 신규 leaf를 담는 상위 집약 노드를 만든다.[^6]

본문 §3.1은 θ(d)=θ₀ exp(λd), Appendix A.1.3은 아래처럼 최대 깊이로 정규화한 식과 실험 설정을 적는다.

> threshold = 0.4 × exp(0.5 × current_depth / max_depth)

본문 식과 부록 식의 깊이 정규화 표기는 다르므로 동일 구현이라고 단정하지 않는다. 부록 기준으로 깊이 비율 0, 0.5, 1에서는 약 0.400, 0.514, 0.659다. 깊을수록 더 구체적인 일치를 요구하는 수치적 기준이다. **매 입력마다 전체 구조를 다시 학습하는 규칙은 아니다.** 다만 삽입 경로 상위 요약·embedding 갱신 비용은 남는다.

이 숫자는 해당 연구의 설정이지 한국어 가족 기록의 검증된 기준이 아니다. 또 의미 유사도로 만든 집약 계층이 사람이 원하는 Topic의 ‘범위 포함’과 같다는 보장도 없다. 별도 전역 재정리 trigger까지 제공하는 알고리즘으로 설명하지 않는다.

### 11.4 xMemory: 배치, 수정 발동, 수정 후보 평가를 분리

Appendix A.2·B에는 질문과 직접 연결되는 규칙이 있다.[^2]

| 결정 | 논문에서 확인한 기준 |
|---|---|
| 기존 그룹 attach / 신규 그룹 | 신규 component와 가장 가까운 centroid의 cosine > 0.6 |
| split 검토 | 그룹 크기 cap 12 초과; 분할 후보의 pairwise similarity 기준 0.65 |
| merge 검토 | A.2는 singleton 그룹을 명시; B는 merge threshold 0.65 명시 |
| 수정 후보 선택 | 그룹 조직 목적함수 f의 개선이 가장 큰 후보 |
| 링크 유지 | group/component kNN, k=10; 영향받은 이웃으로 갱신 범위 제한 가능 |

본문은 넓거나 비일관적인 그룹의 split, 작거나 고립된 그룹의 merge를 설명한다. 구현 상세 A.2는 크기·singleton 조건을 구체화한다. 서로 다른 수준의 설명을 모두 독립적인 수치 trigger가 구현된 것처럼 확대하지 않는다.

목적함수는 f(P)=SparsityScore(P)+SemScore(P)다. 전자는 N²/[K Σ nₖ²], 후자는 그룹 내부 component–centroid cosine 평균과 그룹 간 기하에 대한 가중치를 결합한다. 즉 **수정 발동 조건**과 **어떤 수정이 더 나은지 평가하는 점수**가 별도로 있다.

단, 균등 크기 그룹에서는 위 sparsity 항이 K와 무관하게 1이므로 그 항만으로 ‘그룹 수를 줄일수록 무조건 좋다’고 해석할 수 없다. 전체 Topic 그래프의 범위 포함·ACL·탐색 품질을 평가하는 보편 척도도 아니다. 이 해석은 식에 대한 분석이다.

attach는 온라인, split/merge는 드물게 국소 적용하도록 설명한다. **전체 재학습 없이 수정한다는 방향은 질문에 맞지만, split 후보 생성은 graph-based local clustering이다.** 따라서 지금의 제약에서는 목적함수/trigger를 설계 재료로 검토할 수 있을 뿐, 그 분할 알고리즘을 그대로 채택하지 않는다. LLM이 수정 후보를 만들도록 바꾸는 것은 가능한 별도 설계안이지 이 논문의 검증된 구현이 아니다.

### 11.5 A-MEM·Hindsight: 링크가 있고, 숫자의 역할은 서로 다르다

A-MEM은 cosine 순위로 top-k 이웃을 고른 뒤 LLM이 실제 링크를 판정한다. 숫자는 **관계 후보를 줄이는 필터**이며, 링크 생성의 최종 결정은 의미 판단이다. 노트는 여러 관련 묶음에 동시에 연결될 수 있다. 그러나 이 방식에 root/sub 방향 판정이나 전역 재구축 cutoff가 포함되어 있다고 볼 수는 없다.[^9]

Hindsight §4.1.4에는 semantic link의 cosine threshold θs, 시간 링크의 exp(-Δt/σt) 가중치, 동일 엔티티를 언급하는 기억 사이의 링크가 있다. 이들은 서로 다른 이유로 관련 기억을 찾는 수치·관계다. **semantic similarity는 관련성의 기준이지 어느 쪽이 부모인지의 기준이 아니다.** 인과 링크는 LLM 추출이며 사실 근거 검증이 별도로 필요하다.[^8]

Hindsight의 observation은 엔티티별 파생 종합이다. 논문의 백그라운드 재생성과 후속 구현 설명의 증분 개선은 구분한다. 둘 모두 Topic 계층 전체의 품질 악화를 측정해 재구축하는 기준은 아니다.[^8][^16]

따라서 Memory 소속, Topic의 상위 관계, 계층 밖 관련 링크를 분리해야 한다는 기존 방향은 유지된다. 다만 이 세 판단에 동일 cosine cutoff를 적용하는 것은 위 논문들로 뒷받침되지 않는다.

### 11.6 재구축 필요성에 대한 답은 어디까지인가

| 질문 | 기존 문헌이 제공하는 답 | 남는 공백 |
|---|---|---|
| 새 지식을 기존 묶음에 넣을까? | MemTree의 depth threshold, xMemory의 attach threshold | 대상 동일성·scope·ACL 검증 |
| 어느 부분을 고칠까? | xMemory의 그룹 크기·singleton 등 국소 trigger | 가족 Topic에 맞는 오류 유형·발동 기준 |
| 수정 후보 중 무엇이 낫나? | xMemory 목적함수, adRAP BIC | 고전 군집을 쓰지 않는 Topic 후보 생성·평가 |
| 전체 구조를 언제 다시 만들까? | Zep은 refresh 필요성을 설명 | 품질 악화 기반의 자동 전역 rebuild threshold |
| 정리 후 실제 기억 활용이 나아졌나? | QA 벤치마크·LongMemEval 등 | 운영 trigger와 사람이 읽는 조직 구조의 직접 평가 |

**기존 논문에는 배치와 국소 재정리의 수치 기준이 있지만, 장기 운영의 전역 재구축 필요도를 완성된 하나의 수치로 제공하지는 않는다.** Zep의 periodic refresh나 TiMem의 시간 창 종료는 실행 조건이지 ‘품질이 이만큼 나빠졌음’이라는 측정값은 아니다.[^10][^11]

앞서 제시한 미분류율·소속 이탈률·중복 Topic율·탐색 성공률은 이 프로젝트를 위한 평가 제안이었다. 기존 논문의 이미 검증된 재구축 규칙처럼 읽힐 수 있으므로 이 절에서는 근거 답변과 섞지 않는다. 향후 필요하면 별도의 설계 제안으로 검토한다.

### 11.7 현재 구조 탐색에 남길 설계 재료

현 제약에서 가장 직접적인 재료는 **MemTree의 깊이별 온라인 배치, A-MEM의 후보 검색 후 의미 링크 판단, xMemory의 배치/수정 발동/후보 평가 분리**다. 셋을 합치면 검증된 새 알고리즘이 되는 것은 아니며, 각각의 요소를 독립적으로 확인해야 한다.

장기 사용을 위해 SourceRecord·Canonical Memory·근거는 보존하고 Topic 구조·추천 링크·embedding·판정 정책은 교체 가능한 파생 정보로 둔다. root/sub 판단은 Topic 위치의 문제, 관련 링크는 다른 가지와 연결하는 문제로 남긴다. 객체 정체성과 계층 위치를 분리하는 실무 참고 사례는 Getty와 MeSH, 포함·참조 의미 구분은 SKOS·DCMI에 있다.[^1][^19][^20][^21][^22][^23]

현재의 선택은 특정 서비스를 도입하거나 고전 군집 파이프라인을 구현하는 것이 아니다. **원본을 건드리지 않고 온라인으로 쌓되, 필요한 부분만 수정할 수 있는 구조**를 찾는 것이다. 수치가 있는 부분은 원문 기준을 명시하고, 없는 부분은 우리 설계 과제로 남긴다.

## 12. 최종 권고

현재 구현에는 신규 메모리가 상위 역할을 맡는 기능이 있다. 그러나 사실 객체가 조직 객체를 겸하고, 누적 구조의 병합·분할·재배치를 별도로 다루지 않는다. 부모가 되었다는 이유로 원래 사실을 검색·답변에서 제외하는 규칙은 현재 확인한 경로에는 없다. 역할 혼합과 맥락 확장의 한계는 구분해야 한다.[^L2][^L3][^L7][^L12]

핵심은 **Memory와 Topic을 별도 객체로 분리하는 것**이다. 사실은 Canonical Memory로 축적하고, Topic–Broader Topic은 동일한 Topic 객체 사이의 조직 관계로 표현한다. 지금의 Memory–Parent Memory 관계를 반드시 보존하거나 호환해야 한다는 제약은 두지 않는다.

이 전제에서 xMemory의 수정 가능한 그룹, MemTree의 원본 보존, Hindsight의 사실·파생 정보 분리, SKOS의 계층·관련 관계 구분을 참고할 수 있다. 이는 기존 서비스를 채택하자는 권고가 아니라, 직접 이해하고 구현할 작은 도메인 모델을 위한 설계 재료다.[^1][^2][^6][^8]

계층 밖의 관련 링크는 부모 관계와 분리한다. 신규 소속의 적합도, 의미상 상위 관계의 점수, 재정리가 필요한 오류·탐색 신호는 서로 다른 수치다. 기존 문헌의 수치 기준은 MemTree의 깊이별 배치와 xMemory의 attach·split·merge 및 후보 목적함수에 있다. 이들은 전역 Topic 재구축의 보편 기준이 아니며, 고전 군집 기반 후보 생성은 구현 대상에서 제외한다. 구체 threshold는 검증 가능한 정책으로 남겨 모델과 함께 교체할 수 있어야 한다.

> Memory는 Memory대로 쌓이고, 계층과 링크를 가진 Topic 구조는 Memory를 훼손하지 않고 갈아끼울 수 있어야 한다.
