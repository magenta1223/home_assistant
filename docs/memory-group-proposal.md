# Memory와 Group 중심의 메모리 구조

- 상태: 이전 중간 제안, 미구현
- 현재 설계: [Memory와 Topic 그래프 설계](topic-structure-proposal.md). Topic을 검색용 Group으로 사용하고, 입력 단위의 ACL 변경과 원문 확인을 기본 경로에 포함하는 방향으로 대체되었다. 아래 내용은 이전 논의의 기록이다.
- 기준: [메모리 구조 판단기준](topic-adoption-criteria.md)
- 방향: 별도 Topic 모델을 두지 않고 Memory를 기본 단위로 사용한다. Group은 검색을 위한 묶음이다.

## 1. 두 가지 역할만 구분한다

**Memory는 기억할 내용이고, Group은 관련된 Memory를 모아 찾기 쉽게 만드는 묶음이다.**

예를 들어 다음 세 기록은 각각 Memory다.

```text
Memory 1: 제주 여행은 8월 10일부터 12일까지다.
Memory 2: 여행 예산은 80만 원이다.
Memory 3: 숙소는 공항 근처로 예약했다.

Group: 위 세 Memory를 함께 찾아볼 수 있도록 묶는다.
```

기억의 내용은 Memory에만 저장한다. 같은 내용을 Topic이라는 별도 문서로 다시 관리하지 않는다.
Group에 들어갔다고 Memory의 내용이나 권한이 바뀌지는 않는다.

## 2. Memory의 역할

Memory는 Agent가 찾아 읽고 답변에 사용하는 기본 기록이다.

| 정보 | 의미 |
|---|---|
| ID | 같은 Memory를 구분하는 고유한 값 |
| 내용 | 기억할 사실, 규칙, 사건, 결정 등 |
| ACL | 이 Memory를 사용할 수 있는 사용자 범위 |
| 근거 | 이 내용이 어떤 원본 기록에서 나왔는지 확인할 정보 |
| 메타데이터 | 기록한 사람, 생성 시각 등 |

ACL은 접근 제어 목록이다. 예를 들어 `{A, B}`이면 A와 B를 위한 작업에서 사용할 수 있다.
한 Memory의 내용은 하나이며 사용자별로 다른 본문을 만들지 않는다.

Memory를 직접 읽는 주체가 Agent여도 사용자 권한은 필요하다. A의 질문에 답하는 Agent는
A에게 허용된 Memory를 사용해야 한다. 서비스가 여러 사람의 자료를 보관한다는 이유로
모든 자료를 한 번에 Agent에게 주지는 않는다.

## 3. Group의 역할

Group은 어떤 Memory들을 함께 살펴볼지 정한다. 개념적으로 필요한 정보는 묶음의 ID와
포함된 Memory 목록이다. 구체적인 필드와 저장 방식은 구현 단계에서 정한다.

- 하나의 Memory를 여러 Group에서 찾을 수 있다. 내용의 사본을 만들지는 않는다.
- Group에 들어가지 않은 Memory도 직접 검색할 수 있다.
- Group을 나누거나 합쳐도 Memory의 ID·내용·ACL·근거는 유지한다.
- Group을 없애도 그 안의 Memory는 삭제하지 않는다.
- Group 자체에 독립적인 본문이나 공유 권한을 두지 않는다.

Group은 처음부터 계층으로 만들 필요가 없다. 같은 단계의 묶음으로 시작하고, 묶음을 다시
묶는 것이 검색에 도움이 되는지 확인한 뒤 계층을 검토한다. Memory 간 관련 연결이 필요한지도
별도로 판단한다. 이번 제안에서 새 관계 필드를 미리 확정하지 않는다.

## 4. 권한은 Memory에서 판단한다

하나의 Group이 다음 기록들을 가리킨다고 하자.

| Memory | 사용할 수 있는 사용자 |
|---|---|
| 여행 일정 | A, B, C |
| 숙소 예약 | A, B, C |
| 개인 부담금 | A, B |

C의 질문에 답할 때는 일정과 숙소 예약만 Agent에게 전달한다. 같은 Group에 있다는 이유로
개인 부담금도 전달하지 않는다. 비공개 Memory의 이름·ID·개수도 노출하지 않는다.

Group 구성은 시스템 내부의 검색 정보다. Agent에게 Group 전체를 먼저 보여주고 비공개 부분을
무시하라고 하는 방식은 사용하지 않는다. 허용된 Memory를 고른 뒤 전달한다.

초기 Group에는 Memory들을 종합한 본문을 만들지 않는다. 나중에 Group 이름이나 요약을
자동 생성하면, 그것도 비공개 내용을 담을 수 있으므로 별도로 공개 범위를 다뤄야 한다.
Memory만 걸러도 요약은 안전해진다고 가정하지 않는다.

### 기존의 권한 변경 요구는 어떻게 되는가

앞선 Topic 설계에는 새로운 사용자를 추가하여 기존 본문 전체를 공유하는 요구가 있었다.
이 요구는 남아 있지만 **현재 구현된 Memory의 ACL은 생성 후 바꾸지 않는 방식**이다.

따라서 Topic에서 정한 변경 규칙을 기존 Memory에 그대로 적용하지 않는다. 앞으로 Memory의
ACL 변경을 허용할지, 원본을 유지한 채 승인된 재공유 기록을 만들지는 별도로 결정해야 한다.
Group에 사용자를 추가하는 것으로 이 문제를 우회하지 않는다.

## 5. Agent가 하는 일

새 기록이 들어오면 Agent는 허용된 자료 안에서 관련 Memory를 찾고, 이미 아는 내용인지
새로운 내용인지 판단한다. 보존할 내용을 기록하고 적절한 Group에 배치한다.

기억을 사용할 때의 흐름은 다음과 같다.

```text
사용자의 질문
  → 사용할 수 있는 Memory 범위 확인
  → 직접 검색하거나 관련 Group을 이용해 후보 탐색
  → 필요한 Memory와 근거 확인
  → 답변
```

Group을 이용하는 검색도 권한을 먼저 고려한다. Group 분류가 잘못되거나 아직 분류되지 않은
Memory도 있을 수 있으므로, 반드시 Group을 거쳐야만 검색할 수 있게 만들지는 않는다.

기록이 쌓이면 Agent는 너무 넓은 Group을 나누고, 비슷한 Group을 합치며, Memory의 배치를
조정할 수 있다. 이는 검색 구조의 변경이다. 원본 내용의 수정·삭제나 ACL 변경과는 별개다.
내용의 오류나 변경 사항을 어떻게 기록하고 이전 내용을 보존할지도 따로 정해야 한다.

## 6. 중복과 규모

같은 내용을 사용자마다 자동으로 복사하지 않는다. 같은 공개 범위에서 근거와 의미까지
확인하여 재사용할 수 있는 Memory는 재사용한다. 단어가 비슷하다는 이유로 서로 다른 기록이나
변경 이력을 합치지는 않는다. 비공개 범위가 다른 기록은 따로 존재할 수 있다.

이미 Memory가 1만 개 있다면 원본을 유지한 상태로 Group을 구성할 수 있다. 초기 분류 작업은
필요하지만, 이후 작은 변경마다 전체를 다시 정리하는 방식은 피한다. 새 기록과 관련된 부분부터
정리한다. Group 개수나 크기에 대한 기준은 실제 검색 결과를 보면서 정한다.

사용자 1만 명을 지원해야 한다는 요구도 유지한다.

- 사용자별로 전체 Memory와 Group을 복제하지 않는다.
- 한 질문에 모든 Memory를 Agent에게 전달하지 않는다.
- 검색과 Group 정리는 한 번에 처리할 양을 제한한다.
- Group 때문에 검색 누락이 늘지 않는지, 답변에 필요한 근거를 적은 비용으로 찾는지 확인한다.
- Memory의 수, 권한 분포, 동시 요청 수를 정한 뒤 성능을 측정한다.

사용자 1만 명과 Memory 1만 개는 서로 다른 조건이다. 현재는 구조를 제안하는 단계이며
1만 명 규모의 성능이 검증된 것은 아니다.

## 7. 이번에 정한 범위와 남은 결정

이번 방향은 **Memory에 내용·ACL·근거를 두고, Group으로 검색 대상을 정리하며, 별도 Topic은
도입하지 않는 것**이다. Group의 독립 본문, 권한 상속, 필수 계층은 도입하지 않는다.

후속 결정은 다음과 같다.

- Memory 내용과 ACL의 변경·재공유·이력 보존 방식
- Group을 만들고 나누고 합치는 기준
- 서로 다른 ACL의 자료를 함께 묶을지와 권한을 고려한 검색 방식
- Group의 검색용 이름·설명이나 계층이 실제로 필요한지

이 문서는 개념 설계다. 기존 데이터의 내용·권한이나 런타임 코드를 변경하지 않는다.
