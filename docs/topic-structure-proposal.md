# Memory와 Topic 그래프 설계

- 상태: Topic 모델·영속화 유지. LM 생성·자동 배치 구현 제거 (2026-10-10). 생성 방식·검색·표시·재정리는 미구현
- 기준: [메모리 구조 판단기준](topic-adoption-criteria.md)의 최신 합의
- 이 문서는 이전의 독립 문서형 Topic 제안과 Memory + Group 제안을 대체한다.

## 1. 핵심 구조

**Memory는 원자적 사실을 저장하고, Topic은 여러 Memory를 압축해서 표현하는 검색용 묶음이다.**
Topic끼리는 관련 관계로 연결한다. 사실의 전체 맥락은 Memory가 가리키는 원문 evidence에서 확인한다.

| 개념 | 역할 |
|---|---|
| Memory | 질문에 필요한 사실을 찾는 단위. 내용·ACL·근거를 가진다. |
| Topic | 짧은 설명과 분류별 Memory 참조를 가진다. 관련 Topic과 연결된다. |
| Evidence | 사실이 나온 원문. 적용 조건·예외·전체 맥락을 확인하는 근거다. |

여기서 Topic은 앞서 논의한 xMemory의 Group처럼 검색 범위를 줄이는 역할을 한다.
원문을 삭제하거나 사실을 대체하는 압축이 아니다. 이 역할을 참고하되 xMemory 알고리즘 전체를
그대로 채택한 것은 아니다.

## 2. Memory: 독립적으로 사용할 수 있는 사실

Memory는 ID, 사실을 설명하는 내용, ACL, evidence 참조, 생성 시각 등의 정보를 가진다.
Memory끼리 직접 연결하지 않는다. 한 Memory는 여러 Topic에 속할 수 있다.

**Source는 한 번 저장하면 불변이며, Memory도 생성 이후 ACL만 변경할 수 있다.**
Memory의 content·evidence 참조·ID·생성 시각은 변경하지 않는다. Topic 소속은 Memory 본문의
변경이 아니라 Topic이 관리하는 참조의 변경이다. Memory ACL은 `allowedUserIds`를 활용하며,
PUBLIC 표현과 원문 열람 권한의 일관성은 별도로 구체화한다.

원자적이라는 말은 무조건 짧은 한 문장으로 자른다는 뜻이 아니다.
사실을 올바르게 이해하는 데 필요한 대상·버전·조건·주의점은 함께 적는다.

예를 들어 가상의 기술 문서에서 다음 Memory들을 추출할 수 있다.

```text
Memory 1: 시스템 X v2의 조회 API는 한 번에 최대 5,000건을 반환한다.
Memory 2: 시스템 X v2는 조회 조건을 나눠 여러 번 호출할 수 있다.
          다만 호출 사이 데이터가 변경되면 중복이나 누락이 발생할 수 있다.
```

한 입력이 하나의 사실만 담고 있다면 Memory 하나가 될 수 있고, 여러 사실을 담고 있다면
여러 Memory가 될 수 있다. 원문 전체를 반드시 하나의 Memory로 만들지는 않는다.
다른 내용이 입력되면 새로운 Source와 Memory로 저장한다. 기존 Source나 Memory content를
덮어쓰지 않으며 별도 Source 버전 모델을 도입하지 않는다. 새 기록이 이전 사실을 자동으로
무효화하는 것은 아니며, 사실 간 정정·대체 판단의 상세 규칙은 이번 설계에서 정하지 않는다.

## 3. Topic: 압축된 설명과 Memory 목록

Topic은 짧은 설명, 분류별 Memory 참조, 관련 Topic 목록을 가진다.
다음은 개념을 설명하기 위한 JSON이며 실제 저장 형식을 확정한 것은 아니다.

```json
{
  "id": "topic1",
  "description": "제주 여행에 관한 기록",
  "memories": {
    "여행일정": ["memory1"],
    "숙소예약": ["memory2"],
    "개인부담금": ["memory3", "memory4"]
  },
  "relatedTopics": ["topic2", "topic3"]
}
```

분류명은 Topic 안의 Memory를 찾기 위한 간단한 이름이다. 별도 하위 Topic이나 고정된 관계 종류를 뜻하지 않는다.
Memory를 여러 Topic에서 참조해도 내용과 근거를 복사하지 않는다.

Topic의 설명은 검색할 범위를 알려준다. 자세한 사실은 Memory에서 읽고, 설명만으로 최종 답변을 확정하지 않는다.
같은 Topic 안에 서로 다른 입력에서 나온 Memory가 모일 수 있고, 이들의 ACL도 서로 다를 수 있다.

### 구현 모델 결정 (2026-10-07)

`Topic`은 양수 `Int` ID, 비어 있지 않은 설명, `Map<String, List<Int>>` 형태의 분류별 Memory
참조를 가진다. 분류명은 Topic 내부의 이름이며 공백만 있는 이름과 빈 분류는 거절한다. 같은
분류 안의 Memory ID 중복은 거절하되, 같은 Memory를 다른 분류나 다른 Topic에서 참조할 수 있다.
단계적 생성을 위해 분류가 아직 없는 Topic은 허용한다. Memory ID도 양수여야 하며 실제 대상의
존재·현재 접근 권한은 application·저장 경계에서 확인한다.

관련 관계는 `TopicRelation`에 별도로 표현한다. 작은 Topic ID를 첫 번째에 두므로 반대 방향의
제안도 같은 관계가 된다. 직접 생성하거나 복사해도 양수·서로 다른 두 대상·정렬 순서를 검증한다.
`relatedTopics`는 관계 저장소에서 양쪽 끝점을 조회하여 구성할 예정이며 관계 의미를 없앤 것이
아니다. domain은 부모·루트·순환 제한이나 프레임워크 의존성을 갖지 않는다. Topic 변경은 Memory
참조만 다루며 본문·근거·ACL이나 Source를 수정하지 않는다.

저장은 Topic 본체·분류별 소속·정규화된 관련 관계의 세 테이블로 나눈다. trusted internal
`TopicMaintenanceStore`는 생성·소속 추가·관계 추가를 한 transaction으로 확정하며 기존 소속을
대체하지 않는다. 생성 key는 재시도 시 같은 Topic ID로 돌아가고, 같은 key의 설명이 다르면
실패한다. 없는 대상이나 저장 실패는 전체 변경을 롤백한다. 이 내부 조회에는 혼합 ACL 정보가
포함되므로 사용자 검색·응답 context로 직접 연결하지 않는다. 배치 중인 기록의 복구 경로는
다음 use case 단계에서 정한다.

## 4. 그래프는 Topic 사이에만 둔다

Topic 하나를 그래프의 점인 노드(Node), relatedTopics를 통한 연결을 선인 엣지(Edge)로 본다.

```text
조회 API의 제약 Topic ─── 대량 데이터 처리 Topic
        │                        │
        └──── 데이터 일관성 Topic ─┘
```

연결은 양방향의 관련 관계다. 상위·하위 구분이나 필수 계층은 없으며 순환을 허용한다.
연결을 추가할 때 순환 검사는 하지 않는다. 대상 존재·수정 권한·중복은 확인하며 자기 자신과는 연결하지 않는다.

Topic이 커져 검색 대상을 충분히 줄이지 못하면 여러 Topic으로 나눈다. 크기뿐 아니라 서로 다른
내용이 과도하게 섞였는지도 판단한다. 비슷한 Topic의 병합과 연결 재정리도 가능하다.
분할·병합은 Memory의 소속과 검색 설명을 바꾸는 작업이며, Memory의 ID·내용·근거·ACL을 바꾸지 않는다.
분할 후 여러 Topic에 관련된 Memory는 복수 소속을 유지할 수 있다.

## 5. ACL: 같은 입력의 Memory와 원문은 함께 공유한다

ACL은 누가 정보를 사용할 수 있는지 나타내는 접근 권한이다.
여기서 입력은 하나의 ACL을 지정하여 등록한 원문 단위다. 하나의 입력에서 추출한 Memory들은
같은 공유 범위를 가진다. 원문이 여러 조각으로 저장되어도 이 원칙은 같다.

```text
원문 입력 X: ACL {A, B}
 ├─ Memory 1: ACL {A, B}
 ├─ Memory 2: ACL {A, B}
 └─ Memory 3: ACL {A, B}
```

**같은 입력에서 나온 Memory 1을 읽을 수 있다면 Memory 2·3과 그 원문도 읽을 수 있어야 한다.**
각 Memory를 사용할 때 ACL을 확인하지만, 같은 입력에 속한 기록들의 공유 범위가 따로 달라지게 하지는 않는다.

### 권한은 생성 이후 변경할 수 있다

승진이나 역할 변경으로 C에게 과거 기록을 공유할 수 있다. 입력 X의 공개 범위에 C를 추가하면
그 입력의 원문과 Memory 1·2·3을 함께 읽을 수 있게 한다. 이미 생성된 기록에도 적용한다.

이 변경 때문에 Memory 내용을 다시 만들거나 Topic 소속을 옮기지는 않는다.
사용자를 제거하면 이후 해당 입력의 원문과 Memory를 새로 조회할 때 현재 ACL로 접근을 제한한다.
다만 살아 있는 대화 session에 이미 전달된 문맥과 생성된 답변은 session이 유지되는 동안 계속
사용할 수 있다. ACL 변경만으로 session을 강제 종료하거나 기존 문맥·답변을 차단하지 않는다.
session이 살아 있어도 새로 검색하거나 원문을 읽을 때는 현재 ACL을 확인한다.
기존 10분 idle lease를 유지하며, 만료·종료된 session의 문맥을 새 session에 그대로 넘기지 않는다.
새 session은 현재 ACL에 따라 정보를 조회한다. 이미 사용자에게 전달된 메시지나 읽은 정보는
소급 삭제·회수하지 않는다.
공유 범위를 바꾸는 주체와 승인 절차는 별도로 정하며 Agent의 정리 작업에 자동으로 맡기지 않는다.

공유 범위 변경은 불변 Source의 내용을 수정하는 작업이 아니다. 원문과 파생 Memory의 열람 범위를
일치시키는 권한 저장·조회 방식은 후속 설계에서 정하며, Source 자체의 수정 API를 전제하지 않는다.

현재 구현은 생성 후 변경하지 않는 ACL을 사용한다. 위 내용은 새 설계의 요구이며,
이 문서를 작성하는 것으로 기존 데이터의 권한이 바뀌지는 않는다.

### Topic은 공유 단위가 아니다

서로 다른 입력의 Memory들은 같은 Topic에 모일 수 있다. Topic 전체를 공유하는 별도 ACL은 두지 않는다.
사용자나 ACL 조합마다 같은 주제의 Topic을 자동으로 복제하지 않는다.

Agent에게 Topic을 전달할 때는 다음과 같이 처리한다.

- 현재 사용자가 읽을 수 있는 Memory만 남긴다.
- 남은 Memory가 없는 분류는 제거한다.
- 사용할 Memory가 하나도 없는 Topic은 결과에서 제외한다.
- 비공개 Memory의 ID·내용·개수와 비공개 정보가 드러나는 연결을 전달하지 않는다.
- 짧은 설명과 분류명도 정보이므로, 비공개 내용이 담겼다면 그대로 전달하지 않고 내부 검색용으로만 사용한다.

권한을 확인하기 전에 비공개 자료를 답변 Agent에게 먼저 주고 무시하라고 하지 않는다.
Agent가 누구의 질문에 답하는지에 따라 사용할 수 있는 정보가 결정된다.

## 6. Evidence: 조각난 사실에서 전체 맥락으로 돌아가는 경로

원문에서 여러 Memory를 추출하더라도, 각 Memory는 같은 원문을 evidence로 참조할 수 있다.
원문 전체를 Memory마다 복사해 보관한다는 뜻은 아니다.

```text
Memory 1 ─┐
Memory 2 ─┼─→ 불변 Source X
Memory 3 ─┘
```

Memory들이 서로 다른 Topic에 배치되어도 원문 참조는 유지한다.
Memory 3만 검색되었더라도 그 원문을 읽으면서 Memory 1·2에 해당하는 전제와 예외를 확인할 수 있다.
모든 관련 Topic이 검색 상위권에 올라와야만 정확한 답을 할 수 있는 구조에 의존하지 않는다.

evidence가 조각으로 저장된다면 같은 입력의 어느 부분인지, 앞뒤 문맥이 무엇인지 확인할 수 있어야 한다.
Source ID는 변하지 않는 원문을 가리킨다. 내용이 다른 입력은 다른 Source로 저장하므로
과거 Memory의 evidence를 새 내용으로 교체하거나 Source 버전을 별도로 관리하지 않는다.
같은 원문을 참조한다는 이유만으로 여러 Memory를 서로 독립적인 추가 증거로 세지는 않는다.

## 7. 기본 정보 접근 과정

첫 구현에서의 기본 경로는 다음과 같다.

```text
사용자 질문
  → Topic 검색
  → 권한에 맞는 관련 Memory 선택
  → 선택한 Memory의 원문 맥락 확인
  → 근거를 바탕으로 응답
```

1. **Topic 검색:** 질문에 관련된 묶음을 찾아 검색 범위를 좁힌다. 사용자에게 허용된 Memory가 있는 후보를 찾는다.
2. **Memory 선택:** 후보 Topic에서 질문에 필요한 사실을 고른다. Agent에게 전달하기 전에 현재 ACL을 확인한다.
3. **원문 확인:** 선택한 사실의 적용 조건·예외·맥락을 확인한다. Memory 문장만 보고 곧바로 결론을 내리지 않는다.
4. **응답:** 확인한 사실과 조건에 근거하여 답하고, 확인하지 못한 부분을 확정된 사실처럼 말하지 않는다.

원문 확인은 항상 모든 원문을 통째로 읽는다는 뜻은 아니다. 짧은 입력은 전체를 읽고,
긴 입력은 해당 사실과 조건·예외를 확인할 수 있는 범위부터 읽는다. 맥락이 부족하면 읽는 범위를 넓힌다.
같은 원문을 여러 Memory가 참조하면 한 응답 안에서 같은 부분을 중복해서 읽지 않는다.
필요한 맥락을 확보하지 못했다면 충분히 확인한 것으로 처리하지 않는다.

## 8. 추가 탐색은 필요할 때만 한다

다음은 가능한 확장 경로이며 기본 절차에서 전부 수행하지는 않는다.

```text
검색된 Topic
 ├─ 관련 Topic → 그 Topic의 Memory
 └─ 선택한 Memory → 원문 → 같은 원문의 다른 Memory
                              └─ 그 Memory가 속한 다른 Topic
```

| 추가 탐색 | 사용하는 경우 |
|---|---|
| 연결된 Topic 조회 | 현재 근거만으로 질문의 일부에 답할 수 없을 때 |
| 같은 원문의 다른 Memory 조회 | 다른 사실을 확인하거나 추가 검색으로 이어갈 단서가 필요할 때 |
| 그 Memory가 속한 Topic 조회 | 새로운 근거가 있을 만한 정보 묶음으로 이동할 때 |

원문을 이미 읽었다면 그 원문에서 추출한 Memory를 모두 다시 읽을 필요는 없다.
조건·예외가 불명확하거나 근거가 충돌할 때 추가 탐색한다. 답에 필요한 근거와 조건을
확인하면 멈춘다. 이미 읽은 대상을 반복해서 읽지 않고, 읽을 양과 확장 횟수를 제한한다.
한도 안에서 근거가 부족하면 그 한계를 응답에 남긴다. 전체 그래프를 끝까지 따라가지는 않는다.

## 9. Agent의 구성·정리와 규모

Memory 추출은 기존 분석 경로를 사용한다. Topic은 LM으로 생성하지 않는다.
Topic 생성·배치·설명과 연결 정리의 구체적인 방식은 별도로 정하며, 현재 자동 실행하지 않는다.
새 입력이 기존 사실을 반복하는지, 변경 사항인지 구분하되 기존 Source와 Memory content는 수정하지 않는다.
같은 사실이라도 출처와 공유 범위가 다르면 단순 중복으로 합치지 않는다.
서로 다른 입력을 하나의 Memory로 통합하는 상세 규칙은 이번 초기 설계에서 정하지 않는다.

사용자 1만 명이 이용해도 검색·권한 확인·정리를 감당할 수 있어야 한다.

- 사용자마다 전체 Memory와 Topic의 사본을 만들지 않는다.
- 한 질문에서 읽을 Topic·Memory·원문의 양을 제한한다.
- 새로운 정보가 들어오면 관련된 일부 Topic부터 정리한다.
- Topic 재정리 때문에 Memory와 원문을 다시 작성하지 않는다.
- 원문을 확인하는 비용까지 포함하여 검색 속도·정보 누락·답변의 정확성을 평가한다.

사용자 1만 명과 Memory 또는 Topic 1만 개는 서로 다른 조건이다. 전체 사용자 수 1만 명을
지원하는 것이 목표이며 동시 접속자 수·자료량·성능 수치는 구현과 검증 단계에서 구체화한다.
현재 성능이 검증되었다는 뜻은 아니다.

## 10. 이번 설계의 범위

초기 구현의 중심은 Memory 추출과 원문 보존, Topic 배치·검색, ACL 확인, 원문 맥락 확인이다.
연결을 따라 여러 번 탐색하는 기능과 Topic 분할·병합의 구체적인 알고리즘은 이후 단계에서 확장할 수 있다.

입력별 권한 변경의 승인·반영 방법, 비공개 정보가 섞인 Topic
설명을 안전하게 전달하는 방법은 구현 전에 구체화해야 한다. 이 문서는 개념과 동작을 정하며
데이터베이스 구조나 별도 저장 객체를 추가로 확정하지 않는다.

### 초기 작업 순서 (2026-10-07 이력)

2026-10-06 실행 계획 피드백에 따라 Topic 데이터 구조를 먼저 확정한다. 기존 `childrenIds`와
Memory tree placement는 제거하고 Topic 전용 배치를 새로 만든다. 새 DB로 시작하는 전제이므로
기존 DB migration은 계획하지 않는다. 이는 실제 DB 삭제·초기화를 실행한다는 뜻은 아니다.

Topic 검색과 Memory 선택은 데이터 구조 확정 후에 다룬다. 현재 conversation context 구성은
유지하고, 화면·표시 API는 지금 설계하지 않는다. 위 기본 정보 접근 과정은 최종 목표이며
현재 단계에서 검색·응답·화면을 모두 구현하라는 범위가 아니다.

### 현재 구현 결과 (2026-10-10)

Topic 모델·분류별 Memory 소속·양방향 관계와 명시적 원자 저장 기능은 유지한다.
사용자 요청에 따라 LM Topic 생성 adapter·prompt·배치 service·전용 port·재시도 worker와
Memory 분석 이후의 연결을 삭제했다. 미배치 Memory와 최근 Topic 후보를 조회하던 경로도 제거했다.
현재 앱은 Topic을 자동 생성하거나 배치하지 않으며 대체 생성 알고리즘은 아직 정하지 않았다.

Memory 추출·저장·색인 outbox, 현재 ACL로 확인하는 직접 검색, conversation context와 session
정책은 유지한다. 기존 tree 구조·API·화면을 복원하지 않으며 실제 DB 데이터도 변경하지 않는다.
Topic 검색·표시·재정리는 후속 범위다.

이번 삭제로 대체되었다. 삭제 범위와 검증은 [변경 기록](todolist/done/remove-lm-topic-generation.md)에 정리한다.
