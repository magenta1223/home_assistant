# 공유 Topic과 개인 Topic 구조 사이의 절충점

- 조사일: 2026-10-06
- 상태: 조사 및 설계 제안. 기존 설계의 확정 결정이나 구현 변경이 아니다.
- 맥락: [Topic 본문 설계](../archive/designs/topic-content-memory-design.md), [기존 구조 조사](memory-consolidation-and-topic-hierarchy.md)

## 1. 결론

권장 후보는 **공유 가능한 Topic은 같은 객체로 재사용하고, 개인의 추가 자료나 탐색 목적 때문에 달라지는 구간만 개인 Topic으로 조직하는 방식**이다. Memory·근거·ACL은 공통 저장소에서 보존한다.

이는 전역 단일 트리와 사용자별 전체 트리 복제의 중간이다. 하나의 Topic ID에는 하나의 title·contents·ACL·하위 참조를 유지한다. 같은 Topic을 보는 사람은 같은 본문을 읽는다. 다른 본문이나 하위 구성이 필요하면 별도 개인 Topic을 만든다. 동일 ID의 본문을 사용자별로 교체하지 않는다.

문헌은 공유 지식의 재사용, 국소 확장, 공유/개인 기억의 병행을 뒷받침한다. 그러나 가족의 immutable ACL, Topic 자체 본문, 자동 분할·병합을 함께 평가한 완성형 해법은 이번 조사에서 확인하지 못했다. 이 문서의 조합과 도입 순서는 프로젝트에 대한 설계 제안이다.

## 2. 확인한 선행 사례와 적용 한계

| 자료 | 확인한 내용 | 참고할 부분 | 그대로 적용할 수 없는 부분 |
|---|---|---|---|
| W3C SKOS Primer §2.4, §3.2 [1] | 같은 개념을 여러 concept scheme에서 재사용하고 기존 개념에 새 개념을 연결해 국소 확장할 수 있다. | 공통 정체성을 유지하면서 여러 조직 구조를 허용한다. | ACL이나 생성 본문 설계가 아니다. SKOS 기본 어휘만으로 관계가 어느 scheme 소속인지까지 구분하지는 못한다. |
| Collaborative Memory, 2025, §3·§6 [2] | private/shared 기억을 병행하고, 생성 때 사용한 자원 등의 provenance와 현재 권한에 기반한 읽기를 다룬다. | 공유와 개인 기억을 함께 두고 파생물에도 권한 경계를 적용한다. | 사용자별 Topic 계층·분할을 검증한 연구가 아니다. 모의 다중 사용자 환경과 중간 규모 평가 등의 한계를 밝힌다. |
| Letta memory blocks 공식 문서 [3] | 여러 agent가 같은 block을 참조하고 각자 자신의 block도 가질 수 있다. read-only block을 지원한다. | 공통 객체를 복사하지 않고 재사용하며 개인 상태를 따로 둔다. | agent block 공유가 사람별 ACL 보장을 뜻하지 않는다. 계층형 Topic이나 개인 구조 병합을 제공한다는 근거도 아니다. |
| Zotero Collections 공식 문서 [4] | 한 library의 item을 여러 collection에 넣어도 item이 복제되지 않는다. | 사실 저장과 정리 구조를 분리한다. | 개인/그룹 library 사이의 이동·복사는 별도 문제다. 전역 원본 하나를 여러 사용자 ACL로 공유하는 구현 사례로 확대 해석하지 않는다. |
| HiPS, 2026 preprint, §3–4 [5] | 공통 memory 관리 전략과 필요한 사용자에 대한 개인화 규칙을 분리한다. | 모두에게 전체 개인화를 적용하기보다 차이가 필요한 경우만 추가한다는 방향. | 공유하는 것은 관리 전략이다. 비공개 사실의 공동 학습·Topic 공유가 안전하다는 근거가 아니다. |
| xMemory v4, §3·Appendix A [6] | 기억 조직의 split/merge 점수와 검색 중 불확실성 감소 판단을 구분한다. | 구조 갱신의 평가 대상 집합과 검색 시점 판단을 분리한다. | 다중 사용자 ACL이나 본 문서의 혼합 구조를 검증한 알고리즘이 아니다. |

## 3. 전역 구조와 사용자별 구조만으로 해결되지 않는 것

전역 구조를 모든 자료로 최적화한 다음 비공개 노드를 숨기는 결과는, 각 사용자의 visible 자료만으로 최적화한 결과와 일반적으로 같지 않다. 비공개 자료가 제목·군집 경계·상위 설명에 영향을 주었다면 단순 필터링은 정보 경계도 보장하지 못한다. 이는 구조와 권한에 관한 설계상 분석이다.

반대로 사용자마다 모든 Topic을 처음부터 만들면 공유 자료의 배치와 본문 생성이 반복된다. 같은 Memory를 참조하므로 원본 복제는 피할 수 있지만, 공통 설명과 구조의 중복 유지비는 남는다.

또한 단순한 표시 순서·접힘 상태의 개인화는 권한별 데이터 차이로 인한 분할 기준 차이를 해결하지 못한다. 실제로 다른 분할이 필요하면 개인 소속 관계나 개인 Topic이 필요하다.

## 4. 권장 후보: 공유 Topic 재사용 + 필요한 구간의 개인 구조

### 4.1 공유 가능한 내용은 한 번 조직한다

- PUBLIC 기록은 공유 Topic의 기본 자료로 사용한다.
- 이미 같은 고정 ACL을 가진 기록들이 지속적으로 함께 관리될 필요가 있으면 그 범위의 Topic을 만든다.
- 모든 ACL 조합에 Topic을 미리 만들지 않는다. 사용자 집합의 교집합으로 새 범위를 자동 생성하지 않는다.
- 기존 allowedUserIds를 변경 가능한 그룹으로 자동 치환하지 않는다.

권한 범위별 조직은 출발점일 뿐이다. 실제 ACL 범위가 많으면 범위별 구조도 많아지므로, 이것만으로 생성 수가 작게 제한된다고 주장할 수 없다. 기존 [운영 참고 §1.2](memory-consolidation-operations-notes.md)에도 같은 scope별 조직이 초기 대안으로 제안되어 있다.

### 4.2 개인 구조는 필요할 때만 만든다

사용자는 자신이 읽을 수 있는 공유 Topic을 같은 ID로 참조한다. 추가 비공개 기록이 생겼다는 이유만으로 전체 개인 트리를 만들지 않는다.

다음과 같은 경우 해당 구간에만 개인 Topic을 만든다.

- 공유 설명만으로 해결되지 않는 종합 내용이 반복해서 필요하다.
- 개인이 볼 수 있는 추가 기록 때문에 같은 주제를 더 세분화할 필요가 있다.
- 여러 공유 범위의 자료를 한 개인의 목적에 맞게 함께 정리해야 한다.

개인 Topic의 생성·제목·본문·배치 판단에는 소유자가 읽을 수 있는 자료만 사용한다. 공유 Topic을 수정하는 작업에는 공유 대상 모두가 읽을 수 있는 입력만 사용한다. 개인 작업의 결과가 공유 구조를 자동 변경하지 않는다.

### 4.3 예시

| 객체 | ACL | 내용과 참조 |
|---|---|---|
| T1 건강 안내 | PUBLIC | 검진 일정과 공통 병원 정보. 가족이 같은 객체를 읽음 |
| T2 나의 건강 관리 | 사용자 A | T1, A의 치료·복약 Topic을 함께 조직하고 A에게 필요한 종합을 보존 |
| T3 나의 운동 계획 | 사용자 B | T1, B의 운동·식단 기록을 함께 조직 |

T1을 A와 B에게 복제하지 않는다. T2·T3의 본문을 T1에 덧붙여 사용자마다 다른 T1 본문을 보여주지도 않는다. 원본 Memory 역시 복제하지 않는다.

단순 추가가 아니라 T1의 기록 자체를 다른 방식으로 분할해야 한다면, 개인 Topic들이 해당 Memory ID를 직접 참조하도록 구성할 수 있다. 이때 일부 조직·설명 중복은 발생한다. 이를 없애려고 전역 Topic 정체성 계층, 무제한 상속, 자동 양방향 병합을 첫 버전에 도입하지 않는다.

### 4.4 유지하는 모델과 추가되는 책임

Topic의 title·contents·ACL·하위 참조 모델을 유지한다. 기존 복수 소속 구조를 사용하면 개인 부모 Topic에서 공유 Topic을 참조할 수 있다. 개인화된 구성은 개인 객체에 저장하고 공유 Topic의 children을 사용자별로 몰래 다르게 해석하지 않는다.

관계 자체가 비공개일 수 있으므로 개인 부모가 만든 연결을 공유 자식의 공개 역참조·건수에 노출하지 않는다. 루트 목록과 기본 탐색 위치를 사용자에게 맞춰 선택하는 책임은 별도로 필요하지만, 그 선택이 자원 ACL을 변경하지는 않는다.

개인 Topic의 근거·입력 버전을 추적한다. 공유 기록이 바뀌면 영향을 받는 개인 설명만 재검토한다. 개인이 직접 작성한 설명은 재생성 가능한 캐시로 취급하지 않는다. 자동 구조 갱신이 이를 삭제·덮어쓰면 안 된다.

개인 구조에서의 분할·삭제는 공유 Topic 삭제를 뜻하지 않는다. 공유 Topic이 재구성될 때 기존 참조를 해결할 방법은 필요하다. 근거 Memory의 안정적인 ID를 유지하면 원본에 대한 의존은 계속 추적할 수 있다.

## 5. entropy와 분할 기준

xMemory에서 조직 목적함수는 sparsity와 semantic faithfulness를 결합한다. predictive entropy는 검색 중 추가 문맥이 답변 불확실성을 낮추는지 판단하는 데 사용한다. 따라서 이를 그대로 'entropy 기반 그룹 분할 알고리즘'으로 소개하면 부정확하다. 별도의 entropy 기반 분할을 설계할 수는 있지만 평가할 분포와 목적을 먼저 정해야 한다. [6]

이 혼합안의 핵심은 점수 종류보다 **어떤 자료 집합에 대해 점수를 계산하고 어떤 구조를 변경할지**를 일치시키는 것이다.

| 작업 | 점수·후보 생성에 사용할 자료 | 변경 대상 |
|---|---|---|
| 공유 Topic 분할 | 해당 공유 범위 모두가 읽을 수 있는 명시된 후보 자료 | 공유 구조 |
| 개인 Topic 분할 | 해당 사용자에게 허용된 명시된 후보 자료 | 개인 구조 |
| 사용자 질의 시 문맥 확장 | 질의자에게 허용된 근거와 현재 문맥 | 해당 요청의 문맥 |

한 사용자의 비공개 기록 때문에 공유 Topic이 분할되지 않는다. 개인 분할이 생겨도 다른 사용자에게 동일 분할을 강제하지 않는다.

공유 구조와 개인 구조를 결합한 결과가 각 사용자의 전체 자료에 대한 전역 최적 구조라고 보장할 수는 없다. 필요한 구간만 재조직해서 비용을 줄이는 절충이다. 개인 자료가 대부분이고 분기 구간이 거의 전체가 된다면 완전 개인 구조가 오히려 단순할 수 있다.

## 6. 남는 비용과 안전 경계

- 개인 구조가 달라지는 구간의 중복 Topic·종합은 허용한다. 전역 주제 유일성은 보장하지 않는다.
- 공유 기반 변경은 관련된 개인 구조의 재검토를 발생시킨다. 무제한 차이 패치·자동 rebase 대신 명시적 참조와 필요한 국소 재검토부터 시작한다.
- 개인 Topic 공유는 별도 공개 범위 변경이다. 같은 이름이라는 이유로 개인 자료를 공유 Topic에 승격하지 않는다.
- 권한 회수 시 링크뿐 아니라 제목·본문·검색 자료 등 파생 내용도 차단·재검증해야 한다. 갱신을 지연할 수 있어도 권한 차단을 지연해서는 안 된다.
- 캐시나 생성 결과를 재사용하려면 입력 자료의 ID·버전, 생성 정책, 허용 범위를 확인해야 한다. 사용자 두 명의 현재 열람 집합이 같다고 미래 공유 계약까지 같다고 보지 않는다.
- 혼합 구조는 모든 자료가 공유되거나 모든 사용자가 완전히 다른 자료를 보는 경우에는 불필요한 관리 계층이 될 수 있다.

## 7. 도입 판단을 위한 작은 비교 실험

같은 canonical Memory와 ACL을 사용해 다음 세 후보를 비교한다. 운영 데이터를 변경하지 않는 별도 평가로 진행한다.

1. 공유 범위별 Topic만 사용.
2. 모든 사용자에게 독립적인 전체 Topic 구조 생성.
3. 공유 Topic 재사용과 필요한 구간의 개인 Topic 병행.

공개 자료만 가진 사용자, 공개+개인 자료를 가진 사용자, 서로 겹치는 제한 ACL 자료를 가진 사용자를 포함한다. 질문별로 그 사용자가 실제 읽을 수 있는 근거를 기준으로 평가한다.

- 검색·답변에 필요한 허용 근거를 얼마나 찾는가.
- 한 주제를 이해하기 위해 읽어야 하는 노드·토큰이 얼마나 되는가.
- 공유 Memory 하나의 변경에 필요한 본문 생성·구조 갱신 수는 얼마인가.
- 개인화가 필요한 구간과 재사용 가능한 공유 구간의 비율은 얼마인가.
- 숨겨진 자료의 변경이 공개 제목·본문·분할에 영향을 주지 않는가.
- 권한 회수 뒤 기존 파생 설명이나 캐시가 노출되지 않는가.

측정 전에는 고정 분할 임계값, 특정 개인화 비율, 비용 절감률을 확정하지 않는다. 현재는 공유 Topic을 단일 ACL로 구현하고, 개인 구조는 반복되는 필요가 확인된 구간부터 허용하는 것이 제안이다.
